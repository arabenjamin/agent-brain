## Architecture Summary

See `project-docs/architecture_context.md` for skill registry table, initialization order, and mechanics. See `project-docs/STATUS.md` for current tool counts and feature status.

**Nodes:**
- `Task` - High-level goals with `id`, `goal`, `context`, `success_criteria` (measurable definition of done — used by evaluator step), `status` (created/in_progress/completed/failed/blocked)
- `Note` - Stored text memories with optional vector `embedding`, `access_count`, `last_accessed_at`, `note_type` (`semantic`/`episodic`/`reflection`/`consolidated`/`outcome`/`inference`/`claim`/`source_record`/`news`), `next_review_at`, `review_interval_days`, `source_context`, `event_at`
- `Procedure` - Named multi-step workflows with `id`, `name`, `description`, `steps` (JSON array), `created_at`
- `WorkingMemory` - Session-scoped scratchpad entries with `id`, `session_id`, `content`, `role`, `turn_index`, `created_at`
- `Entity` - Named entities extracted from notes with `id`, `name` (unique, lowercased), `entity_type`, `created_at`
- `DynamicTool` - Runtime-defined MCP tools with `id`, `name` (unique), `description`, `input_schema` (JSON), `created_at`
- `AgentJob` - Background job record with `id`, `tool_name`, `args_json`, `priority` (0-3), `status` (queued/running/completed/failed/dead/parked/cancelled), `attempt_count`, `max_attempts`, `result_json`, `error`, timestamps, `session_id`, `parent_job_id`
- `ModelSpec` - Registered LLM models with capabilities, cost, and usage stats
- `ToolDef` / `ContextProfile` / `ModelDef` - **Self-model meta-graph** (Phase 0b of the Agent Constructor plan). Generated by introspection in `services/self_model.rs` at the end of every `build_skills()` — never hand-edit: the tool registry, `contexts/*.yaml`, and the DuckDB model catalog are the sources of truth, and stale nodes are deleted on each sync. `(:ContextProfile)-[:ALLOWS]->(:ToolDef)` edges mirror profile tool allowlists (`allows_all: true` when the profile has no allowlist). Chains/schedules are not duplicated here — `(:SchedulerChain)`/`(:ScheduledTask)` already are the graph representation.
- `BrainVersion` - **Singleton `{id:'current'}`** recording the commit this process is running (`sha`, `subject`, `branch`, `dirty`, `seen_at`, `deployed_at`). Written by `sync_code_version()` in `services/self_model.rs`, right after the meta-graph sync. When the sha differs from the stored one it also writes ONE episodic note (`source_context: "code_version <sha>"`) listing the changed files; an unchanged sha is a no-op, so restarts cost nothing.

  This replaced a `post-commit` → `scripts/self_update.py` round-trip (deleted 2026-08-10). That script re-derived over HTTP what the process already knows, and got it wrong: it parsed `analyze_own_structure`'s **Markdown** output as JSON inside a bare `except: pass`, printing `tools at runtime: 0` on every commit since March, and it indexed `result[0]` on a dict. It also fired on `git commit` — before the rebuild it triggered had finished — so the note described code that was not yet running, and it only ever covered a local `git commit` (not `docker compose restart`, CI, or a pull on another machine). Reading HEAD in-process at startup reports **what is actually loaded**. The hook is now just `docker compose up -d --build`.

**Relationships:**
- `(:Note)-[:RELATES_TO {similarity: float}]->(:Note)` — auto-created when similarity ≥ 0.75
- `(:Note)-[:SUMMARIZED_BY]->(:Note)` — source notes pointing to their consolidated summary
- `(:Note)-[:REFLECTS_ON]->(:Task)` — reflection/outcome notes linked to the task they critique
- `(:Note)-[:PART_OF]->(:Note)` — semantic chunk linked to its parent note
- `(:Note)-[:MENTIONS {count}]->(:Entity)` — entity mentions extracted from note content
- `(:Note {note_type:'inference'})-[:DERIVED_FROM]->(:Note)` — inference notes citing their sources
- `(:Task)-[:SUBTASK_OF]->(:Task)` — sub-tasks (`create_task` with a parent)
- `(:Task)-[:DEPENDS_ON]->(:Task)` — dependency edges for task ordering
- `(:DynamicTool)-[:USES]->(:Procedure)` — links a dynamic tool to its step definition
- `(:AgentSpec)-[:CONSTRUCTED_FOR]->(:Task)` — a constructed agent linked to the task it was dispatched for
- `(:AgentSpec)-[:PERFORMED {score, passed, at}]->(:Task)` — graded outcome written by the queue's evaluator hook; the constructor's reuse-before-construct prefers specs with avg score ≥ 3.5
- `(:ApiContext)-[:EXPOSES]->(:ApiEndpoint)` — endpoints ingested by `ingest_api` (see below). `:ApiEndpoint {api_name, method, path, summary, operation_id, parameters, security, tags}` MERGE'd on `(api_name, method, path)`, so re-ingest updates in place.

### Native REST API ingestion (`ingest_api`)

`ingest_api` in `HttpSkill` (`skills/http.rs`) ingests a REST API's endpoints from **one of three sources** (pass exactly one) and stores each operation as an `(:ApiEndpoint)` under an `(:ApiContext)` via `[:EXPOSES]`. This is the properly-resurrected agent-api "spec → endpoint graph" idea (the old `ingest_openapi` was a doc-comment ghost; the code was never ported).
- **`spec_url`** — a direct OpenAPI 3.x / Swagger 2.0 doc (JSON **or** YAML).
- **`docs_url`** — an HTML docs page. Deterministically detects the linked spec: scans the page, then its referenced `.js` (Swagger UI keeps the `url:` in `swagger-initializer.js`); when a page advertises several specs (the Swagger demo dropdown) it **prefers one on the same host as the page**; unwraps `host=https://…` map entries. If a spec is found it ingests via the spec path (`source: html_spec`). If **no** spec is linked, it **falls back to LLM extraction** from the page text (`html_to_text` → `generate_json`, `source: html_llm`) — lower confidence (verify before relying on it), used only after deterministic detection fails. Needs the injected `Arc<dyn LlmProvider>` (unmetered `SharedLlm`); absent it, a clear error.
- **`codebase_path`** — a local dir searched (bounded, skips `node_modules`/`target`/…) for an existing spec file (`openapi`/`swagger` `.json`/`.yaml`, `api-docs.json`) → parse it (`codebase_spec`). No spec file → **build-from-routes**: `find_route_files` scores source files by route-marker density (axum/actix, FastAPI/Flask, Express, Spring, gin/echo), feeds a bounded corpus of the top files to the LLM, which returns the endpoint list (`source: codebase_generated`, lower confidence — it merges router prefixes and infers params from signatures, but reads registrations not a contract).

Spec-based parsing is a `serde_json::Value` walk — **no LLM**, so no truncation/hallucination. Every operation → method, path, summary, operationId, merged path+operation parameters, security scheme names, tags. base_url resolves 3.x `servers[0].url` (absolute or relative-to-origin) → 2.0 `schemes[0]://host+basePath` → the spec URL's origin. The `(:ApiContext)` records provenance: `source` (`openapi_spec`/`html_spec`/`codebase_spec` are deterministic; `html_llm`/`codebase_generated` are LLM-derived, lower confidence) + `discovered_from`. Endpoints MERGE on `(api_name, method, path)` (idempotent). Persistence (shared by spec and LLM paths, `persist_endpoints`) uses the atomic `UNWIND $endpoints` + `RETURN count` read-back (the dynamic-tool-fix lesson: one query, no cross-connection MATCH, verify the write landed). Fetch/file-read run **in the brain process** (has egress/FS), never the sandbox. Query results with `neo4j_query`. Parser/detection tests: `ingest_api_tests`. All four ingestion routes (spec URL, HTML docs, codebase spec-file, codebase build-from-routes) are implemented; the two LLM-derived sources are labelled lower-confidence rather than deferred. **`prune: true`** turns re-ingest into a true sync: after the upsert it deletes endpoints of the same API not written in this run (older `updated_at`), so a removed route disappears — the result adds `endpoints_pruned`. **The brain keeps its OWN API doc current with it**: `schedules/brain-api-sync.yaml` (weekly) runs `ingest_api(codebase_path=".../crates/app/src/mcp", name="agent-brain", prune=true)` on unmetered ollama-cloud — the brain publishes no OpenAPI spec, so this build-from-routes ingest over its Axum route table IS its self-documentation (`ApiContext` `agent-brain`, ~48 endpoints); step 2 banks a dated endpoint/prune-count record (`source_context: brain_api_sync`). Point the same tool + a schedule at any other service on the network (a spec URL, a Swagger UI page, or a repo) to give the brain a queryable map of that API too.

**Autonomous discovery (`api-scout`).** `contexts/api-scout.yaml` is a spawnable profile (search_web + http_request + ingest_api + notify_user) that scouts the web for free public REST APIs in the brain's interest areas and **ingests the keyless ones** (a spec reachable without an account) while **`notify_user`-flagging the key-gated ones** for a human to supply a key — it never signs up or invents a key. `schedules/api-scout.yaml` drives it weekly via a single `run_agent(agent="api-scout")` step and is **seeded disabled** (`enabled: false`) for review; turn it on with a Cypher `SET s.enabled=true, s.next_run_at=datetime()`. It is the discovery half of the API toolchain; `api-integrator` is the build-a-client half. Requires `SUBAGENT_ENABLED=true`.

### Self-Improvement Loop

`SchedulerService` background task: lists `status=created` Tasks → `goal_to_steps()` → `enqueue_chain()` → marks `in_progress`. After `idle_sleep_after_ticks` (3) idle ticks → `enter_sleep()` (consolidate → prune → snapshot). `notify_activity()` resets the idle count. `QueueService` coordinator runs jobs serially per provider semaphore, retries transient failures, unparks dependents on success.

- **★ Crash recovery respects `max_attempts` — a hung job is NOT immortal.** `reset_running_agent_jobs` used to flip every `running` job back to `queued` unconditionally, which made `max_attempts` meaningless across a restart: a job that **hangs** is never marked failed, so it is still `running` at the next startup and gets resurrected, forever. It now dead-letters jobs already at their cap (with a `j.error` saying so) and requeues only those with attempts left; the count it returns is the REQUEUED count, dead ones logged at WARN. Observed 2026-09-11: an `ingest_media` job on a live stream reached **attempt 29 against a cap of 3**, revived by each restart during a day of rebuilds. **Not media-specific** — any job that hangs rather than failing hits this, which is why the fix is in recovery, not in a per-tool timeout.
- **Dead-job meta-learning:** on retry exhaustion, store a reflection note and — for non-infra tools (`should_meta_learn`) — enqueue an Analyze→Hypothesize→Test→Integrate chain. Guards: `is_transient_infra_error` (skip for quota/rate/timeout/5xx) and `recently_meta_learned` (≤ once/tool/24h).
- **Chain-death task attribution:** `enqueue_chain_owned(steps, session_id, Some(&task_id))` stamps `__owner_task_id` on every step; on step death the coordinator calls `fail_task_with_reason(task_id, reason)`, guarded to `status IN ['created','in_progress']`. `enqueue_chain` is the no-owner wrapper (chat/bedtime/meta-learning).

### Evaluator Loop (Generator-Evaluator)

A Task with `success_criteria` gets a `reflect_on_work` evaluator step appended by `goal_to_steps()`. It parses a `Score: N/5` line; `< min_score` (default 3.5) → mark task `failed` + create a new Task with the critique in `context`. **Retry cap 3** (`handle_evaluator_requeue` counts `"RETRY —"`). **Unparseable output = pass** (`parse_evaluator_score` → `None`; do *not* fabricate a 3.0 and do not grade the AgentSpec). `ChainStep`: `is_evaluator`/`min_score`/`evaluator_task_id`; args `__evaluator_min_score`/`__evaluator_task_id`. A `:SchedulerChain` may carry `evaluation_rubric` to override the goal text. Full story: history § Evaluator Loop.

### Adversarial Critic (pre-flight plan review)

A Task with `success_criteria` also gets an `adversarial_plan_review` step **prepended**. `overall_robustness < min_robustness` (default 2.5) → cancel downstream + `handle_adversarial_requeue()` (mark failed, new Task with critique). **Abort cap 3** (`"ADVERSARIAL ABORT"`). Skipped when: no `success_criteria`, chain `no_adversarial: true`, or context already has `"ADVERSARIAL ABORT"`. `ChainStep`: `is_adversarial`/`n_hypotheses`/`min_robustness`/`adversarial_task_id`. `parse_adversarial_robustness()` defaults 3.0. Also callable directly (KnowledgeSkill); each run stores a `semantic` note `source_context: "adversarial_review"`. Full story: history § Adversarial Critic.

### Externalized Agent Chains

Scheduler routing chains are `chains/*.yaml` seeded as `(:SchedulerChain)` by `init-db` and force-refreshed on the first tick after every startup. `goal_to_steps()` queries Neo4j, falls back to `build_diagnosis_chain()`.

**Chain YAML schema:** `name` (MERGE key), `pattern` (primary CONTAINS), `patterns: [...]` (OR), `priority` (lower = matched first; default chain 9999), `no_evaluator`, `no_adversarial`, `evaluation_rubric`, `steps: [...]`.

- **Matching is plain CONTAINS; priority is the only tiebreak.** A broad substring pattern silently hijacks a specific one if it sorts first — put specific prefixes at low priority numbers, and check no broader pattern outranks a new chain.
- **Template vars** in step `arguments`: `{{goal}}`, `{{goal_topic}}`, `{{task_id}}`, `{{date}}` (local date), `{{now}}` (local instant), `{{weekday}}` (local), `{{file_slug}}`. **Use `{{goal_topic}}` for anything fed to a search engine** (strips the routing prefix). Substitution is **value-level** (`substitute_template_vars` walks parsed JSON, replaces inside string values only — quote/backslash/newline-safe).
- **`{{_prev}}` vs `{{_prev.<path>}}`:** `{{_prev}}` = the previous step's output *after* `extract_result_text` unwraps `answer`/single-column `rows` (lossy by design). `{{_prev.<path>}}` (e.g. `{{_prev.id}}`, alias `{{result.id}}`) resolves a dotted path against the **pre-unwrap** envelope (`prev_result_raw`), never distilled. Unresolvable path → **empty string**, never the literal placeholder (consumers read empty as absent). Both forms may co-occur; paths substituted first; strings inserted raw.
- **Per-step model routing:** a step may declare `required_capabilities: [...]`; `services/model_router.rs` picks the best catalog model **the routing policy admits for the step's purpose and `data_class`** (`services/routing.rs` `route()`; the log names every better-ranked model it skipped, with the reason), routed via the `SELECTED_LLM` task-local (precedence: capability-selected > `USE_LOCAL_LLM` background pin > active config). Metadata: `__required_capabilities`, `__data_class`. **A step is private unless it or its chain/schedule file says `data_class: public`** (the seeders stamp a file-level value onto steps), and private work only reaches `no_log` providers. `ROUTE_CONTEXT` is scoped around the job, so `SharedLlm` judges every fallback rung by the same policy. Guards: `private_reasoning_stays_on_a_no_log_model`, `public_reasoning_routes_to_gpt_oss_like_private`, `private_work_never_reaches_a_training_provider_for_any_capability`. **"Best" = `cost ASC, selection_rank ASC, context_window DESC`** — and since every local/cloud model costs 0.0, **`selection_rank` is the decision** (per model in `models.yaml`, lower wins). Bands: `0–9` reserved (empty since 2026-10-02, when `gemini-2.5-flash` moved from 5 to 98 after failing 2 of 8 reasoning calls at ~31s while `gpt-oss:120b-cloud` failed 0 of 79), `10–99` ollama-cloud (`gemini-2.5-flash` at 98, the band's last rung), `110–199` local, `100–109` free tiers that may train on prompts (Mistral, OpenRouter `:free`), opened to private work for every purpose by their `private_ok_for` (owner's decision 2026-10-10, when the Ollama Cloud free quota ran out), so they are the cloud overflow ahead of local, `210+` paid. **Background fallback** (`SharedLlm::generate`) walks selected → active → `background_fallback_ladder` (models.yaml: Mistral, OpenRouter) → local, each rung admitted by the policy. **An account-wide quota 429** (`ACCOUNT_QUOTA_MARKERS` in `services/budget.rs`, Ollama's "Free usage limit") benches the **whole provider** for an hour, re-probed after; any other 429 benches only the model. Rank is **global, not per-capability**; a single-holder capability is only safe while it stays single. Guards: `selection_order_tests` + `model_config.rs` assert the checked-in `models.yaml` (incl. `reasoning_at_tier2_routes_to_gpt_oss` and `vision_at_tier2_stays_on_the_ollama_cloud_vision_model`). `minimax-m3:cloud` removed 2026-08-31 (left free tier); the seven ollama-cloud entries are the whole free tier. **Gemini free-tier caveat:** `gemini-2.5-flash`/`gemini-3-flash` are catalogued at cost 0.0, which is accurate only on the free tier (429 at the ceiling, no billing) — move them off 0.0 if the deployment ever exceeds it.
- **A step may pin a model: `model: "<catalog model id or name>"`** (`ChainStep.model` → `__model`; HBI plan Phase 10):
  - **Matched exactly** (`model_router::find_model`, case-insensitive), never by substring. A profile's `model_preference` still matches fuzzily (`resolve_profile_model`); a pin does not.
  - **Takes precedence over `required_capabilities`** and goes through the same `SELECTED_LLM`.
  - **A pin, not a preference.** `pinned_config` judges it by the routing policy for the step's data class when the job runs. An unknown or refused model kills the job at once with `Step model cannot run: <reason>` (`STEP_MODEL_ERROR`, no retries, no meta-learning), and the owning task fails with that reason.
  - **The policy's refusal is final; availability isn't.** A cloud pin that later hits quota or a 5xx walks the usual fallback chain, and every rung is in the ledger.
  - **`provider_hint` is derived from the model at enqueue** (`provider_hint_for`: a provider billed `local` gives `ollama`, otherwise the provider's name; only `anthropic` and `gemini` have their own semaphores).
  - **At upsert** (`validation::validate_step_models`, also run by `audit`):
    - an unknown model, or a written hint that contradicts the model's provider, is a hard reject;
    - a pin the policy would refuse right now is a soft `step_warning`;
    - a pinned step isn't asked for a hint.
  - **Why the derivation and the check exist:** the Zero Trust schedule wrote `provider_hint: ollama-cloud` beside the host-local `gemma4:latest`. `model` was ignored then, so nobody could tell what ran.
- **`run_agent` takes `model`** (else a step's `__model`) and `read_only`:
  - the model gets the same exact match and policy check; an unknown or refused one rejects the run with the reason;
  - `read_only` strips write tools, as a chat sub-agent's are stripped: an HBI assist drafts into a form and must never store a note;
  - the result names the `model` the loop started on.
- **A chat turn takes `model`** (`ChatRequest.model`, the HBI header picker). It overrides the profile's pin; an unknown or refused one sends `Error` and `Done` and calls nothing. The front door's `model` names a profile, not a catalog model, and stays separate.
- **`/api/models` rows carry `admission`:** `{background|subagent|chat: {private|public: null | refusal}}`, computed with `RoutingPolicy::admit`, so spend caps and cooldowns show. The HBI `<ModelPicker>` reads it. It is cheap, but a spend-capped paid provider logs its cap warning once per row per request.
- **Paid synthesis (`deep_reasoning`, 2026-10-02).** `cost ASC` sorts every paid model behind every $0 one, so a paid model can only win a capability no free model holds. `deep_reasoning` is held by `claude-sonnet-5` **alone** (guard: `deep_reasoning_is_held_by_sonnet_5_alone`) and is requested by the synthesis `reason` step of the five standing-investigation schedules (intelligence-agency-claims, hardware tripwire, off-grid, SLM watch, tech-dependency synthesis), ~$0.15–0.20 per run, ~$7/month against the `anthropic` cap of $1/day, $10/month. When the policy refuses it (cap reached, `ROUTING_PAID_FOR` unset) no candidate survives and the step runs on its own `provider_hint: ollama-cloud` (gpt-oss), so a spent budget degrades the step instead of failing it. **The Anthropic provider omits `temperature` for models that reject it** (Sonnet 5, Opus 5/4.7/4.8, Fable, Mythos: a 400 otherwise), joins every `text` block (a leading `thinking` block made `content[0].text` empty), defaults `max_tokens` to 16000 (thinking counts against it) and floors its timeout at 300s.
- **`CURRENT_TOOL`** task-local attributes every in-job LLM call to `job.tool_name` in the usage ledger. The **chat path does not use it** — `clients/chat/` records directly (defaulting to `"chat"`). A **sub-agent** run (`delegate`/`run_agent`) is instead labelled by the `USAGE_TOOL_LABEL` task-local, scoped to `subagent:<agent>` in `AgentRunner::run` around the bounded loop (propagates through `join!`, never a `spawn`); before this its LLM cost billed under `chat`, so `run_agent`/`delegate` had **zero** rows in `model_usage` and sub-agent spend was invisible. Query it with `tool_name LIKE 'subagent:%'`. (2026-09-08)
- **`optional: true` on a step** lets a chain survive that step dying: the job is still dead-lettered and reflected on, but the next step gets an `[OPTIONAL STEP FAILED — …]` note as `{{_prev}}` and the owning Task is not failed (`__optional` in the job args; `CHAIN_STEP_FIELDS` lists it). For enrichment the chain can do without — the daily brief's weather and ApiTube fetches, after a ~15-minute outage cancelled the whole 2026-09-30 brief.
- **Distilled handoffs (`distill_prev: true`, `distill_max_chars`, `distill_focus`):** `maybe_distill_prev` compresses upstream output on the **local** model before substitution. Soft budget (overshoots ~50%); only hard guarantee is "never longer than raw". Own `LlmClient` at `num_ctx=16384`. **Never** on a step that persists `{{_prev}}` verbatim, nor on evaluator/adversarial steps. Every failure path falls back to raw. Wired in `learn.yaml`, `git-history.yaml`, `video-learning.yaml`.
- **UI chain** (`chains/ui-frontend.yaml`): frontend keywords → `workspace/ui/{{file_slug}}.md`, `no_evaluator: true`.

### Self-knowledge: making running state visible

A model that can't see running work reports it as absent, confidently. Rules that fix the class:

- `manage_scheduled_task(action=list)` is a **tool** (lean payload; `verbose: true` for the rest); **empty-filter guardrail** returns every name + a warning rather than an empty list. `list_tasks` returns **totals** and leads with open work.
- **Truncated tool results are marked** (`truncate_tool_result` → `[TRUNCATED … INCOMPLETE]`). A `reason` result's declared limits are **hoisted to the front** (`annotate_tool_limits`/`reason_limits_marker`). `search_web` results are **prefixed with a numbered source list** (`search_sources_marker`, accepts `link` or `url`). `prepare_tool_result` is the single annotate-then-truncate entry point; the marker leads so truncation can't drop it.
- Failed protocol steps log at **WARN** (`tool_call FAILED`). A **dropped chat turn is reported** (`forward_chat_events`) instead of vanishing — and separately, an **abandoned** one is too: if the SSE client goes away mid-turn the handler future is dropped, that tail never runs, and the turn leaves no trace at all (on 2026-09-11 a turn ran `search_notes`, spent two gpt-oss calls / ~31K prompt tokens, and vanished leaving only an orphaned user row in working memory — indistinguishable in the logs from a request that never arrived). `TurnAbandonGuard` is a `Drop` guard, because cancellation is the one turn-ending path no `await`-side code can report; it is armed for the whole turn and disarmed once the event stream drains, so it never double-reports the dropped-turn case. ### ScheduledTask ownership (`managed_by`)

Built-in ScheduledTasks live in `schedules/*.yaml` (seeded by `schedule_seeder`); a missing `schedules/` dir aborts startup. The **graph is the runtime authority**; YAML is the definition source only for tasks it owns.

- **`managed_by`:** `yaml` (steps/description/interval force-synced every startup — file edits win, runtime edits overwritten) vs `runtime` (seeder never touches). Transfer via `manage_scheduled_task` upsert `managed_by`.
- **A runtime node shadows its YAML file permanently and silently** (matching is by exact `name`; `sync_yaml_scheduled_task` skips a runtime-owned name). Check `managed_by` before assuming a file is what executes; `manage_scheduled_task(action=list, verbose=true)` is the only routine way to notice.
- **`enabled` is graph-owned** (deliberately not synced) — so pausing survives restarts. Disable with a targeted Cypher `SET`, **not** `upsert` (upsert requires `steps` and force-rewrites description/interval). A `schedules/*.yaml` may set **`enabled: false`** to seed a task OFF on first creation (honored only on create, since `enabled` is never force-synced — `seed_scheduled_task_if_absent`); absent ⇒ `true`. Use it to ship a schedule for human review before it can ever run (e.g. `schedules/api-scout.yaml`). `paused_reason`/`paused_at` record why. **`scripts/pause_cloud_schedules.sh {pause|resume|status}`** disables only cloud-routed schedules; audit targets against the graph (`provider_hint <> 'ollama' OR provider_hint IS NULL`). When a quota goes, check the ledger by `tool_name` first — chat, not schedules, usually spent it. **A chain's cloud cost is a multiplication (once per item), not a rate** — bound the item count before adding `ollama-cloud` to a fan-out step; cap burst and daily total separately.
- **A schedule declares `topic:` and `kind:`** (HBI plan Phase 11; on the node, in `schedules/*.yaml`, in the HBI form):
  - `topic` is a `topics/*.yaml` name, or none for a schedule that spans topics on purpose. `kind` is one of `SCHEDULE_KINDS` (`monitor` · `brief` · `learning` · `maintenance` · `dataset`).
  - **Checked on every write path:**
    - the seeder warns and stores none for a wrong value;
    - `manage_scheduled_task` upsert and REST `POST`/`PUT /scheduled-tasks` reject one (`schedule_seeder::check_labels`);
    - `every_schedule_file_declares_valid_labels` fails the build on a bad file.
  - **The schedule is the one home of the link.** A topic's "Watched by" is computed from `ScheduledTask.topic`; the old `schedules:` list in topic files is gone. A yaml-owned schedule's `topic`/`kind` are force-synced from its file like its steps; a runtime-owned one keeps what the graph holds.
- **REST `/scheduled-tasks` (the HBI's save path) runs the step-model check too** (`validate_step_models`, with the catalog). It still runs no per-step argument-schema check; `manage_scheduled_task` does, because it has the tool registry.
- **What a schedule produced is traced, not guessed** (`GET /api/work/schedules/topic-mix?days=N`, `clients/work.rs`). Each note is counted once, by the first route that reaches it:
  1. **`run_stamp`:** the note's `produced_by_task` is one of the schedule's run records. The queue scopes `CURRENT_OWNER_TASK` around every job, so the note store and `store_claim` stamp every note a job writes, including those written inside a `run_agent` loop.
  2. **`job_result`:** a kept job reported the note's id. **Completed jobs are pruned after about two days**, which is why the stamp exists; job lineage alone covered 2 days, not 30.
  3. **`source_context`:** the note carries a literal `source_context` the schedule's own steps write (`step_source_contexts`). This is how notes from before the stamp are traced; no two schedules share one.
  4. **`claim_of`:** a claim asserted in a note traced by the first three.
  
  Chunks (`PART_OF`) are not counted: their parent is, and only the parent is classified.
- **The verdict** (`mix_verdict`, each note's main topic):
  - fewer than 3 classified notes is `too_few`;
  - a declared topic holding a third of the assessed notes, or the most, `matches`; otherwise `mismatch`, naming the top topic;
  - with no topic declared, a topic holding half is a `suggest`ion; otherwise `spans`.
  
  The HBI shows it on the list row and in the schedule drawer, with the per-route counts.
- **A ScheduledTask's steps are enqueued verbatim** — no `goal_to_steps()`, no adversarial/evaluator, no auto-retrieval. Step prompts must be correct alone; a schedule needing fresh info must include its own `search_web`. **Chat-authored schedules get no validation** → `lint_chain_steps` (`skills/scheduler.rs`) covers: a `reason` past position 1 with no `context`; a persisting step past position 1 not mentioning `{{_prev}}`; a `store_note` with no `source_context`; a `store_note` with an **unrecognized `note_type`** (checked against `VALID_NOTE_TYPES` — a chat-authored schedule stored an `analysis`-typed note on 2026-09-08 that then never labelled/recalled correctly); `semantic` in a web-searching chain; unregistered tool; a chain that never persists; **a step with no `provider_hint`** (omission ≠ local — `use_local` is `provider_hint == Some("ollama")`, so omission falls through to cloud; **and `provider_hint` is a step-TOP-LEVEL field, a sibling of `tool_name`/`arguments` — putting it *inside* `arguments` is silently ignored by routing, so the step runs on cloud. The same 2026-09-08 schedule made exactly this mistake on all six steps while its author reported "configured to use ollama".**). Warnings, not rejections. Runs in `upsert` (`step_warnings`/`needs_fix`) and `audit`. Behavioural half: `BUILD RULE` in `contexts/general.yaml`.
- **A tool argument at step level is a HARD reject** (`misplaced_arguments` in `services/validation.rs`). Serde drops unknown `ChainStep` fields, so `context: "{{_prev}}"` written beside `arguments` never reaches `reason` and nothing errors — the Trump Benefit monitor's reasoning never saw its search results. Only keys the tool's own schema declares are flagged; `CHAIN_STEP_FIELDS` must track `ChainStep`.
- **Deterministic structural validation (HARD reject, `services/validation.rs`).** Distinct from the semantic lint: `manage_scheduled_task` upsert AND `manage_chain` define validate **each step's `arguments` against the tool's own registered `input_schema`** (snapshotted from the registry in `brain_core.rs` alongside `live_tools`) via the `jsonschema` crate, through the shared `SchedulerSkill::hard_reject_steps`, and REJECT the write (nothing saved) on any type/required-field violation or an unregistered tool. This is the classic automated pushback: `ChainStep.arguments` is a free JSON value, so a wrong-typed arg (`query_params:"[object Object]"`, `timeout_ms:"15000"` — the HBI-editor corruption that silently killed the AI Dev Board Job Search schedule every run) passes the shape check and the semantic lint but is caught here before it can be stored. (`manage_chain` did NO validation at all before this.) Object envelope schemas live in the `schemas/` seed dir (`scheduled_task`, `scheduler_chain`, `task`, `context_profile`), loaded once by `validation::load_schema_dir` (`SCHEMAS_DIR`, default `./schemas`); the **envelope layer is wired for schedule+chain** (`hard_reject_envelope` in upsert/define — name/interval/enum/min-items around the steps) and the **`audit` action runs the per-step structural gate over every STORED ScheduledTask** (`structural_errors`), so YAML-seeded tasks are checkable on demand. Note `create_task` already parses typed serde input, so the untyped step `arguments` was the real gap. **Seeder skip-on-boot is deliberately NOT enabled** — verified over all checked-in YAML, a hard boot-skip would silently disable real chains (a conditionally-registered `run_agent` when `SUBAGENT_ENABLED` is off; an invalid enum like the `meta-learn` `note_type: hypothesis` bug fixed 2026-09-09) — dropping a human-committed schedule on boot is worse than a loud warning, and any validator must use the in-process `registry.list()` full set, not the `MCP_TOOL_PROFILE`-bounded HTTP `tools/list`. Full design: `project-docs/VALIDATION_AND_APPLY_PLAN.md`.
- **One-shot Task vs recurring ScheduledTask:** `create_task` fires once on the next tick — cadence words in the goal are inert. Recurrence needs `manage_scheduled_task(upsert, interval_seconds)` or a `schedules/*.yaml`.
- **Reading prior runs:** chunks inherit `source_context` from their parent, so any Cypher retrieving a prior report by `source_context` must add `AND NOT (n)-[:PART_OF]->()`.
- **Critical Tech Dependency schedules** (three-tier standing investigation, each banks searches into a WorkingMemory scratch session and delta's against the prior run): `hardware-tripwire.yaml` (weekly, `hardware_tripwire`, 4 sweeps), `slm-benchmark-watch.yaml` (bi-weekly, `slm_benchmark_watch`, 3 sweeps), `tech-dependency-synthesis.yaml` (monthly, `tech_dependency_synthesis`, no web search — correlates the other two). Also `off-grid-networking-monitor.yaml` (weekly, `off_grid_networking_watch`, 3 sweeps).

### Entity resolution (`services/entity_resolution.rs`, 2026-10-08)

One real thing is one `:Entity`. Schema: `schema.md` § Entity / EntityAlias. Plan: `HBI_REDESIGN_PLAN.md` §3.1.

- **Extraction resolves before it creates.** `extract_entities` asks for names *as written* (capitals kept) through `generate_json` (`{"entities":[…]}`), then resolves each one: alias by name → entity by name → alias by key → entity by key → create. Never go back to a bare `MERGE (:Entity {name})`; that is what made `us`/`u.s.`/`usa`/`united states` five nodes.
- **The key folds spelling, not meaning.** It lowercases, keeps only letters and digits, drops a leading article, and drops a leading title **only before a full name** (`president donald trump` = `donald trump`). It does **not** fold `senator johnson` into `johnson` or `speaker johnson`, which are different people; that pair becomes a `title` proposal. All-digit keys never fold (`911` ≠ `9/11`). Names in the seed's `keep_distinct` never fold (`the hacker news` ≠ `hacker news`).
- **A case-sensitive alias needs capitals in the text.** `us` resolves to United States only when the note has `US`/`U.S.` as a whole word. Lowercase mentions stay on their own `us` node. Case sensitivity applies to every alias sharing that key (`u.s.` keys to `us` as well). The same regex runs in Rust and in Cypher (`upper_pattern`; no lookaround, because Rust's `regex` has none).
- **Automatic merges are curated or spelling-only.** `init-db` runs `sync` on every start. It seeds the `entities/*.yaml` canonicals and aliases, rewrites keys, and folds same-key entities and alias-named entities, after a `pre_entity_merge` snapshot (a failed snapshot means no merges). Everything else (surnames, acronyms, title + surname, plurals, demonyms) is a **proposal** in the Work inbox and the entity drawer. `agent-brain resolve-entities --dry-run` prints the plan.
- **Demonyms resolve to their place** (`entities/demonyms.yaml`, HBI plan Phase 20). At extraction "Chinese hackers" mentions China: the probe is rewritten to the place before lookup, `MENTIONS.surface` keeps "Chinese", `via` records "chinese", and the vote counts it as a location.
  - **A pair the user answered stops it.** If the demonym entity and its place have `NOT_SAME` or `RELATED_ENTITY`, the word is left as itself; if that can't be read, every demonym is left as itself for that note. Remove the word from the YAML too.
  - **Existing demonym entities are proposals** (reason `demonym`, only when the place entity exists), not seed aliases, so `sync` never folds them on its own: "Chinese" is also a language, "Spanish" and "French" too.
  - **The table is generated, then reviewed.** Wikidata's English demonyms of sovereign states and U.S. states, a word two places share dropped (georgian, dominican, congolese), words that usually mean something else dropped by hand (finn, dane, vatican, persian…), and curated entries where Wikidata has none (ukrainian, saudi). The header lists every drop. The generator is described in the plan's Phase 20 outcome.
  - **Background lookups skip demonyms** (`wiki.rs` `WAITING`, coverage): they gave Phase 18's worst picks. "Look up" in the drawer still runs.
- **Every merge is reversible.** It repoints mentions, stamping `via` (or appending `"<id>:<count>"` to `absorbed` when the note already mentioned the target), keeps the old id, type and created_at on the `EntityAlias`, and deletes the old node. `unmerge` (HBI Undo, `POST /api/entities/aliases/{name}/unmerge`, `resolve-entities --unmerge NAME`) recreates it as `distinct: true`. Mentions other aliases absorbed into the same edge stay put. A distinct entity is never folded again, and the seeder skips a curated alias with its name, but the YAML still lists it, so remove it there too.
- **Candidates carry a local classifier's verdict, which only orders them** (`services/alias_judge.rs`, HBI plan §11.10). On idle time, `nimble` on host Ollama (`/v1/systemone`, `ALIAS_JUDGE_MODEL`, `off` to stop) reads up to 2 notes mentioning both names and 2 mentioning each alone, and answers same / related / different with a probability for each. That answer is stored as `ALIAS_VERDICT`. Likely-same pairs sort first, then not judged yet, then related, then different.
  - **It never merges.** Hand-graded live, with the measured field order: 32 of 40 tuning pairs and 25 of 28 held-out pairs right. No confident "same" was wrong.
    - Most misses are cautious (Prince William → related, Oppenheimer → different). Its "different" includes "can't tell", and the HBI labels it "not shown to be the same". A fourth "unclear" option was measured and never chosen.
    - Its wrong "same" answers were all under 0.6: "Kushner" ≠ Josh Kushner (0.41) live, and "General Franks" ≠ Dennis Franks (0.59) before the order fix. So a "same" below `CONFIDENT_SAME` (0.7) shows as "leans the same" and sorts with the unjudged.
  - **Field order is part of the prompt.** The answer depends on the order of the options and of the texts. The first deploy built the request with `json!`, whose map is alphabetical, and Mills / Doug Mills went from different (0.81) to same (0.95). The request is built from structs, which serialize in declaration order, and a test pins the order. Keep any other `/v1/systemone` caller the same way.
  - **Use the stored name, not the surface form.** Feeding the names as written (`Senator Collins`, `Tim Scott`) produced three false "same" verdicts.
  - **A new prompt bumps `PROMPT_VERSION`**, so every pair is judged again. Re-measure on the hand-graded pairs (scratchpad scripts are listed in the plan) before shipping the change.
- **A person's "different" or "related" answer is remembered.** These are `NOT_SAME` / `RELATED_ENTITY` edges, and a pair with either is never proposed again. A merged-away id still opens in the drawer as "merged into X" via `EntityAlias.merged_from_id`.
- **Prune keeps canonicals.** `prune_stale_entities` skips `type_source: seed` and anything with an `ALIAS_OF` pointing at it, and drops aliases left pointing at nothing.
- **The type is a majority vote.** `MENTIONS.type` records each extraction, and the entity takes the most common one (the first note used to fix it forever). A seed canonical's type is fixed.
- **Measure retrieval around a bulk merge.** Entity expansion (`MENTIONS → Entity ← MENTIONS`) feeds retrieval, so a large merge changes what bridges notes. Run `eval-retrieval` before and after, and record the numbers in `engineering-history.md`.

### Topics (`services/topics.rs`, 2026-10-08)

The domains the brain tracks. Schema: `schema.md` § Topic, plan: `HBI_REDESIGN_PLAN.md` §3. History: `engineering-history.md` § Topics.

- **Declared in YAML, assigned by the local model.** `topics/*.yaml` has one topic per file, and its `description` *is* the classifier's definition. Embedding centroids were measured and rejected (F1 0.61 against hand labels, against 0.83 held-out for the classifier). Sharpen a description with what does *not* belong ("general AI knowledge is ai-ml, not agent-brain"); that is what fixed the confusions. All descriptions share one local-model prompt, so keep each short (the test caps the shipped prompt at 3.2k chars; an HBI edit may take it to 3.6k).
- **Main topic first, a second only if it is as central**, at most 2 (`IN_TOPIC.rank`). Asking for "0–3 topics" over-tagged national security onto every war and government story.
- **Every note is accounted for.** Each top-level note is in a topic, assessed as fitting none, waiting, failed (3 tries), or skipped by `topics/_scope.yaml`. `GET /api/topics` returns those counts and they sum to the total. Don't add a filter that drops notes from all five buckets.
- **Skip rules compare coalesced values.** `n.source_context = 'x'` is null for a note without one, `NOT any(…)` is then null too, and the note silently leaves every bucket. That happened (5 notes stuck "waiting"). `SKIPPED_CYPHER` coalesces both sides.
- **The assigner runs only while the brain is idle** (no job `queued`/`running`, no GPU lease). It re-checks every 5 notes, runs batches back to back while idle, and is started only by the HTTP `serve`. `TOPIC_ASSIGNER_ENABLED=false` stops it. The model call is about 0.3 s, but end to end (reads, writes, idle checks) it measured about 56 notes a minute on 2026-10-09, so the whole graph (~13.7k notes) takes about 4 hours of idle time.
- **The version is a hash of every name, description and skip rule.** Changing any of them re-classifies everything. Labels and `source_lists:` don't count. A note the scope newly skips loses its old topics at the next `init-db`.
- **Activity records are skipped, not classified.** `scheduler_dispatch` episodic notes are a goal plus a task id. Classified, they landed in the goal's topic and buried what was learned.
- **The YAML seeds; the graph owns** (HBI plan Phase 14). `Topics::global()` is the graph's set, reloaded after every edit (`topics::reload`), so an HBI edit applies from the assigner's next batch, with no restart.
  - An HBI edit makes the topic `managed_by: runtime`, and the sync then skips it. This is the schedule rule: check `managed_by` before assuming the file is what runs. Reset puts the file's definition back.
  - Deleting a seeded topic leaves a `(:RetiredTopic)`, so `init-db` does not recreate it. A delete also clears `topics_version` on that topic's notes: a reset brings back the same version, and a note still stamped with it would look classified without its topic.
  - `init-db` syncs topics **before** seeding schedules, because a schedule's `topic` is checked against them.
- **An edit is checked before it is written** (`topics::check_def`):
  - the name is a 2–40 character slug, set once, and `map` and `new` are reserved;
  - a description is at most 500 characters;
  - the whole classifier prompt stays at most 3,600 characters;
  - a delete is refused while a schedule declares the topic, and the refusal names the schedules.
- **A topic about the user, or one of their programs, is assigned by rules, not by the classifier** (`assign: rules` + `members:` in its YAML or the HBI form). The model can't tell whose career or which agency a note is about, and a topic in its prompt that is small and personal draws notes that fit nothing else. Measured in Phases 14–15:
  - `career` took anyone's career: 22 of 56 other people's notes kept it, even with "any other person's career … is not career".
  - Renamed `my-job-search`, it halved that on the sample of Career's own notes. Live, all of the first 13 notes it took were strays: a murder trial, an Uber case, a news brief.
  - "intelligence agency" took CIA and FBI stories, and `nia` took the brain's daily stats reports and GDELT summaries.
  - **How a rules topic works:** it is left out of the prompt, so the model can't pick it even by name. A note joins by a `members` rule (`note_type` / `source_context` exactly, `content_contains` case-insensitively in the first 1,500 characters), ranked first, or by hand. The rules are part of the version hash. `topics::reload` applies them at once in Cypher (mirroring `MemberRule::matches`) and drops classifier edges on rules topics, so a rules topic doesn't wait for the hours-long re-classify.
  - **The name still matters** for a classifier topic. Test a new or renamed one on a sample against the sidecar before saving it, and include notes that fit **no** topic in the sample. Phase 14's sample left them out, and missed exactly the failure that showed up live.
- **A program is not a subject.** The NIA's monitors declare `topic: nia`, but their reports are classified by what they are about: a Trump-deal assessment is us-politics or geopolitics. The `nia` topic holds the notes that name the program. The schedule topic mix shows this as a mismatch, and the mismatch is true.
- **The user's word is final** (Phase 15):
  - **Note topics:** topics set in the note drawer are `method: 'manual'` and the note is `topics_locked`. The classifier never picks it, and `topics::reload` stamps it with each new version, so it never counts as waiting. "Let the classifier decide" unlocks it. Deleting a topic unlocks that topic's notes.
  - **Entity hides:** `(:Entity)-[:NOT_IN_TOPIC]->(:Topic)` keeps an entity off that topic's map and entity lists, whatever its notes say. The map, the topic drawer and the entity drawer each show the hides with undo. A merge carries the hides to the surviving entity.
- **How entities relate is computed from shared notes** (`clients/related.rs`, Phase 16; no entity→entity edges exist until Phase 17).
  - **Rank by strength, never by raw count.** Strength is shared notes ÷ √((mentions A + 3) × (mentions B + 3)). Raw counts put C-SPAN (184 notes) first for 30 of the 300 entities it shares notes with; strength puts it first for 1. The +3 keeps two entities that share their only note from scoring a perfect 1.0. `strength` in Rust and `STRENGTH_CYPHER` must stay the same formula (a test checks them together).
  - **Every pair drills to its notes** (`/api/entities/pair`). A topic scope counts only that topic's notes and leaves out entities the user keeps out of it.
- **Claims get their entities from an idle-time loop, not at write time.** `store_claim` writes in raw Cypher, so before Phase 16 none of the 4,546 claims had a `MENTIONS` edge, and no entity view could see the most entity-dense notes. `spawn_claim_entity_backfill` takes claims with no mentions and no `entities_at`, newest first, and stamps every one, so it covers the backlog and each new claim (`CLAIM_ENTITY_BACKFILL=false` stops it).
  - **Claims use their own prompt.** With the general extraction prompt the local model answered `[]` for 22 of 30 claims, most of which name someone; the claim prompt left 5 of the same 30 empty, and those name nothing. The general prompt is unchanged, because it hasn't been measured on long notes.
- **Typed relationships** (`services/relations.rs`, Phase 17): `(:Entity)-[:RELATES {type, method, status, evidence}]->(:Entity)`.
  - **A closed vocabulary** in `relations/*.yaml` (`RELATIONS_DIR`). Each type has a definition, a label and its inverse ("works for" / "employs"), and the entity types allowed at each end. Many real things are typed `concept`, so the "thing" ends allow it. `related_to` is the user's only (`extract: false`), and the merge list's "related" answers fold into it.
  - **The user's edges are final; extracted ones are proposals.** Accept makes one active, reject keeps it as `rejected`, and `propose` never revives a rejected edge (it only counts `seen_again`). Removing the user's own deletes it. Relabelling removes the old type (rejecting an extracted one) and sets the new one as the user's, with the old evidence.
  - **Extraction runs on the cloud, measured first.** The local Gemma-4-E4B got 2 of 8 relations right on the tuning set, and with stricter prompts it answered `[]` even for its own prompt's example. On 30 fresh held-out claims, gpt-oss:120b-cloud was right 8 of 9 times leniently and 5 of 9 strictly. So `schedules/relation-extraction.yaml` pins `model: gpt-oss:120b-cloud` (`no_log`, $0), and its proposals wait for review (Work → Feed → relationships to review).
  - **The prompt's examples are the measured failures:** something belonging to an entity ("a Ford plant in Mexico") taken for the entity, a forum's location taken for its host's, and a refused or alleged relationship taken as stated. `validate` drops anything naming an entity the claim doesn't mention, a type outside the vocabulary or a user-only one, an entity related to itself, and ends of the wrong type, and the tool reports each drop with its reason.
  - **Keep a measurement set frozen.** Claims gain entities while the backfill runs, so a sample drawn by query shifts between runs. The Phase 17 script saves its sample on first use.
- **Reference links** (`services/wiki.rs`, Phase 18): `(:Entity)-[:REFERS_TO {status, method}]->(:WikiItem {qid})`, which Wikidata item and English Wikipedia article an entity is.
  - **Background lookups cover only entities a claim mentions.** A lookup sends the entity's name to Wikimedia, and names also come from the résumé, job-search chats and other private notes. Claims come from videos, articles and news. `source_record` does not count, because the résumé is stored as one. `link_entities` without `entity_id` selects only claim-mentioned entities, and with `entity_id` but no `on_demand` it returns `skipped_private` without calling anyone. The drawer's "Look up" sets `on_demand`.
  - **The model chooses from the search, never the top result.** Wikidata's top hit was wrong 13 of 37 times (DRM → Digital Radio Mondiale, PNG → the image format). `pick_prompt` gives the candidates with their kinds and up to 3 claims, says the filed type may be wrong (the racehorse Shergar is typed `person`), and asks for 0 when unsure.
  - **The second search is for named things only.** When the model answers 0, it may suggest up to 2 search terms. That found garbled and short names (Pento Barbatale → pentobarbital, Kapo → Estonia's Internal Security Service). But for `concept`, `event` and `programme` entities it found a match that wasn't there: "system intelligence" → AGI, a makemore video → WaveNet, "Cuomo Full Show" → CNN's old Cuomo Prime Time. So those types never get one.
  - **Nationality words still slip through.** "Italian" → Italy, and "Chinese" → the People's Liberation Army through the second search, despite the prompt's rule. Picks are proposals; the drawer's "Not this" rejects one for good.
  - **Wikidata labels may be `mul`, not `en`.** Many items keep their name only as a language-neutral `mul` label (Albert Einstein has no English one), so every request asks for `en|mul`.
  - **One request at a time, with a contact.** Three parallel lookups drew HTTP 429, then a 41 s `Retry-After`. All Wikimedia calls go through one gate: serialised, at least 1.1 s apart, a 429 pauses every lookup for its `Retry-After`, and the run ends early saying so. `WIKIMEDIA_CONTACT` (in the user agent) is required; without it nothing is looked up, and the HBI says so.
  - **One place pins the model.** The drawer's "Look up" enqueues the `entity-linking` schedule's own `link_entities` step with `{entity_id, on_demand: true}`, so its `model: gpt-oss:120b-cloud` pin and the routing policy apply as for the hourly run.
  - **Two entities on one item are a merge candidate** (`reason: wikidata`), and the alias judge gives it a verdict like any other. A pair the user already answered (`NOT_SAME`, `RELATED_ENTITY`) is not proposed again, even when they share an item (MSS ↔ Ministry of State Security).
  - **Topics get a URL, not a lookup.** Most topics are the user's own groupings with no article, so `reference` is set in the topic form or YAML. It is outside the topic `version`, so editing it classifies nothing again.
- **Kinds** (`services/entity_kinds.rs`, Phase 19): `entity_type` stays the coarse class the extractor gives; `kind` is the fine one (country, municipality, news outlet…), derived from the reference link.
  - **Derived, not judged.** The linked WikiItem's instance-of classes are walked up subclass-of to the roots in `entities/kinds.yaml`. The **nearest** root wins (ties: file order), and a `fallback` kind (organisation, website, product) only when no specific kind is reachable. Matching in file order over the whole tree made YouTube an event and every U.S. state a country; a fallback that could win at hop 0 made the WSJ a website. Wikidata's upper ontology is tangled, so keep roots narrow: "geographic location" (Q2221906) took the PRC government.
  - **A disagreement is a question, never a retype.** A link's kind applies only when its coarse type agrees with the filed one (decision §12.7.1: proposed links too). Otherwise `type_question_qid` is set and the Feed shows "entity types to check". On the first 226 items, a quarter of the disagreements came from wrong links.
  - **The user's type is final.** `type_source: manual` (set in the drawer, or by answering "keep" / "use the reference") stops the extraction vote (`entities.rs`) and the questions. "Let the brain decide" removes it and re-runs the vote. A seed's type stays fixed. "Keep" remembers the item in `type_kept_qids`, so that link never asks again.
  - **Wikimedia pages are never references.** A candidate whose class label starts "Wikimedia " (disambiguation, set index, list) is dropped before the model sees it, a pasted URL to one is refused, and a proposed link to an item whose classes reach a `refuse` root is withdrawn.
  - **Classes are cached** as `(:WikiClass)` through the Wikimedia gate. `link_entities` refreshes kinds after its lookups (at most 60 requests a run; an incomplete walk waits for the next), and a link decision in the drawer refreshes that entity. `link_entities {limit: 0}` refreshes kinds only.
  - **`link_entities {limit: 0}` only refreshes kinds** (it clamped to 1 until Phase 21).
  - **Editing `kinds.yaml` re-derives every kind** (its hash is `kind_version`), from the cache. It shares `entities/` with the alias seed, whose loader ignores its keys; don't give it a top-level `types`, `titles`, `articles`, `keep_distinct` or `entities` key.
- **`wiki_background`** (`services/wiki_background.rs`, Phase 21) reads Wikipedia for a question: named subjects only, each article picked from Wikidata's candidates, then its lead, best-matching section and most-cited domains. **It is not in the gap chain:** three measured rounds failed to show a gain that held up twice, and the free cloud quota it needs (up to 5 calls a gap) is shared with `entity-linking` (HBI plan Phase 21 outcome, v2 and v3). If it is ever wired in, make the step `optional: true`: a refused step model dead-letters on the first attempt and would cancel the gap. Measure any v2 with `scripts/replay_gap_wikipedia.py` on `eval/gap_wikipedia_replay.json` before wiring it in, and remember that the reason step's 3,000-character distillation squeezed the background out entirely.
  - **Replaying gaps needs the old answers removed:** past runs stored "## Gap synthesis" notes, 1–7 per question, which `search_notes` hands straight back.
  - **Two runs of one query differ.** 2 of 8 same-query pairs differed materially, so compare arms on more cases or repeated runs.

### System health, logs, registry (`clients/system.rs`, 2026-10-08)

- **One call answers "is the machine all right?"** That call is `GET /api/system/health`. It probes every service in `architecture/components.yaml` (`ARCHITECTURE_DIR`) in parallel with a 3 s timeout, then adds the scheduler, the queue, the GPU lease, provider budgets and the running version. It returns `issues` worst first, so the UI never derives what is wrong itself.
- **A new dependency is a YAML entry, not code.** Give it a `name`, a `label`, a `probe` (`neo4j` | `duckdb` | `http`), a `url_env` plus a `path` (and an optional `strip_suffix`), and `required` when the brain is broken without it. An unset `url_env` is *not configured*, never *down*: the brain runs without optional sidecars. The response shows endpoints as scheme://host:port only, with no path and no credentials.
- **Logs are about the machine.** `GET /api/logs` filters by `level`, `target` (prefixes, `-prefix` to drop), `quiet` (prefixes shown only at WARN or above), `q` and `after`, and reports `matched`, `buffered` and `oldest`, so a capped page says it is capped and how far back the buffer reaches. The buffer holds 2,000 lines (500 covered about an hour). The HBI's "hide routine activity" quiets the scheduler, queue, skills, chat and knowledge-write modules (`ACTIVITY_TARGETS` in `hbi-frontend/src/api/system.ts`); their warnings and errors always show. Tasks and jobs belong in Work, not Logs.
- **Registry is read-only.** `GET /api/system/registry` lists skills and their tools, dynamic tools, agents, chains, MCP servers (whether each one's secret env var is set, never the secret), providers and the component list. Edits go through Settings.

### Chat context dock (`hbi-frontend/src/lib/chatDock.ts`, 2026-10-08)

- **The dock is derived from the turn's events, never asked of the model.** What ran is the `tool_call` / `tool_result` stream, paired in order. What the turn wrote is the ids in the results of tools that write (`WRITE_VERB` in `chatDock.ts`, or `manage_*` with a writing `action`). What it read is the ids in the rest. A link in the answer is checked against the text every tool returned or was sent this turn. A new writing tool with a different verb belongs in `WRITE_VERB`, or its ids show under Read.
- **Ids resolve in one call:** `POST /api/lookup` (`clients/search.rs`) takes up to 60 full ids or 8+ character hex prefixes. A prefix resolves only when exactly one node has it, and everything unresolved comes back in `missing`, so a cited id that names nothing is shown, not dropped.
- **A chat that names no profile gets the front door.** The HBI sends `context_profile` only when the user picks an agent; `/api/contexts` reports `default_profile` (`CHAT_DEFAULT_PROFILE`, or `null` when the server picks per message). Never default the picker to a profile name: that silently bypasses the deployment's router.

### Living architecture (`services/architecture.rs`, 2026-10-08)

- **The architecture is computed, never written down.** `GET /api/architecture` builds it from what the brain already knows: `(:ToolDef)` (skills and tools, re-synced at every start), `(:ContextProfile)`, `(:SchedulerChain)`, `(:ScheduledTask)`, `(:McpServer)`, `(:DynamicTool)`, the provider registry, `components.yaml`, and the routes **parsed from the router source** (`mcp/http_transport.rs`, `include_str!`). Don't add a route anywhere else: a router outside that file would be invisible to the view. The brain writes no TSX and no layout: a model hand-editing a diagram is the `doc-update` failure in a harder medium (HBI_REDESIGN_PLAN.md §4).
- **`architecture/layout.yaml` holds only what can't be derived:** groups (selectors `kind:name`, a trailing `*` matches a prefix, an exact selector beats a wildcard), the edges between groups, and the container topology. **A new skill is unplaced until you add it to a group.** The view shows it under "Unplaced", and a selector that matches nothing as stale, instead of dropping either silently. A new tool, schedule, agent or route area under `/api` needs no edit.
- **The topology is checked against compose.** `the_layout_topology_matches_docker_compose` fails when `docker-compose.yml` gains a service, a network or a published port that `layout.yaml` doesn't have, and `the_shipped_layout_places_every_route_and_its_edges_name_groups` fails on an unplaced route area. Update the layout in the same change.
- **Snapshots are set arithmetic.** `snapshot_architecture` (first step of the weekly `brain-api-sync`; `dry_run` to look without storing) stores an `(:ArchSnapshot)` with its diff against the previous one and a one-line summary written by code. A baseline is taken at the first start. "What changed" in the HBI compares the **live** inventory with the newest snapshot, so it never lags a deploy.

### Curiosity engine (`chains/fill-knowledge-gap.yaml`)

Gap tasks (`"fill knowledge gap: …"`) come from `spawn_gap_tasks` (a video's `## FOLLOW UP`) and the daily news schedule. **A gap task must make sense without its source (2026-10-01).** A gap chain searches the graph and the web with no access to the video it came from, so `spawn_gap_tasks` drops follow-ups that point back into it (`is_standalone_gap`: `(Context:`, `(Inferred)`, "the final scene", "this practice", "the speaker", …; under four words), the video-learning prompt asks for at most two general topics a year-from-now reader would want ("NONE" allowed, no sports), and `GAP_TASKS_DAILY_MAX` (20) caps the day. Before this ~30 gaps/day were mostly trivia ("the subtle wave from the daughter in the final scene"), and their answers fed consolidation. The chain searches **both** graph (`search_notes`) and web (`search_web`) — a gap is by definition what the graph lacks — banks into `gap-{{task_id}}`, reassembles, answers under `## ANSWER` (cited) / `## WHAT THIS ADDS` / `## STILL UNKNOWN`. Priority **15** so it stops losing its own tasks to `learn.yaml`. Search steps use `{{goal_topic}}`. Full story: history § Curiosity engine.

- **A gap is a question a few searches can settle, not an essay prompt (2026-10-03).** Asking for "general topics worth knowing a year from now" swapped trivia for "What are the long-term implications of…", which no search answers. The video FOLLOW UP and news Open Questions prompts now ask for what/how/who/when/how-much questions naming the concrete thing, and `is_standalone_gap` drops essay markers (`implications`, `how might`, `intersect`, …). Answers are capped: ≤5 cited fact bullets.
- **A distilled handoff must fit the distiller's window, or its middle vanishes unmarked** (2026-10-10). `maybe_distill_prev` reads at most 24,000 characters, the first 16,000 and the last 8,000. The gap chain's ALREADY KNOWN section ran to 20,500 characters at the median (67,000 max), so 73 of 143 runs silently lost a median 9,000 characters of stored notes. The reassembly step now caps that section at 15,000 characters with a "stored notes cut here: N more characters" marker. The web section never exceeded 7,412, so the whole handoff stays inside the window (verified on the three largest: 21–23k). It is the only distilling step that overflowed. A new one that reassembles working memory needs the same cap.

### Epistemics: claims, source records, retrieval labelling

Three note types the brain used to conflate: `semantic` (knowledge the brain established), `source_record` (what an external source *said* — video summaries, `news`), `claim` (one checkable proposition + evidentiary status).

- **`(:Note {note_type:'claim', claim_status, asserted_by, asserted_at})`** with `ASSERTED_IN`/`CORROBORATED_BY`/`CONTRADICTED_BY` edges. Status is **derived** from edges (`recompute_status`), never asserted; verification attaches evidence and recomputes, never edits the claim. Support+contradiction → `disputed`; absence → `unverified` (never refuted).
- **`label_claims` (`services/knowledge/labels.rs`) runs in BOTH retrieval paths** — miss one and the unlabelled copy still reaches context. Prefixes claims `[CLAIM · status · asserted by X · date]` and source records `[SOURCE RECORD — …]`, with a humanised age. `claim`/`source_record` are **excluded from consolidation source selection** (consolidation would launder the status away).
- **Claim kind** (`event`/`attribution`/`mechanism`) separates "was asserted" from "is true"; corroborated `attribution` renders "corroborates that it was asserted, not that it is true". **`classify_domains`** tiers corroborating domains (primary/established/unclassified; role-less SourceLists only) mechanically and rides it in the label; verification is **never gated** on tier, and `state_media` SourceList domains are **labelled only** (`incl. state media (…)` in the tier). **`check_independence`** requires `MIN_INDEPENDENT_DOMAINS` (2) distinct domains **among the results the judge cited** (`sources: [...]` → `resolve_cited_links`), excluding self-referential and `platform` SourceList domains (Facebook, Instagram, YouTube…: citable, never counted — the one gate, on whether a domain is a source at all, not on reputation). **Platforms match on each cited link's host** (`DomainRoles::is_platform_link`), so an entry can name a subdomain: `markets.ft.com` is a company press-release feed, `ft.com` is FT journalism, and both share the registrable domain `ft.com`. Never count uncited results: a LinkedIn post plus four unrelated hits passed the old any-two-results rule. **Syndication counts once** (`check_independence_titled`): cited results whose headlines reduce to the same `story_key` (outlet suffix peeled — a tail of ≤ 4 words after `|`/`-`/`—`/`–`; keys under 4 words never merge) are one story, so independence counts headline-merged groups of domains, not domains. Search APIs do not reliably flag reposts: Webz returned one Al Jazeera article on aljazeera.com and Yahoo News, neither marked syndicated. Edge carries `r.sources` (cited links) + `r.domains` (counted). Does not solve true independence.
- **Echo results are dropped before judging** (`drop_echo_results`): a search-results-page link (also dropped earlier, in `search_web` itself, for every caller), or a title/snippet containing the whole claim (≥ 40 chars), is the query echoed back, not evidence. The evidence note stores the filtered set. Full story: history § Epistemics (2026-10-06).
- **★ Verifier input is EXTERNAL ONLY.** `verify_one` calls `search_web` with `prior_knowledge: false`; a `supports` verdict must cite a result link (`source_is_in_results`, else `support_rejected_unsourced`); `evidence_domains` counts result `link`/`url` fields only, never URLs in body text. Why: from 2026-09-12 the graph-first block fed the judge our own note restating the claim, and corroboration went 41% → 84% (e.g. "My legs!" corroborated by a sleep.com article). Data reset: `scripts/reset_selfcorroborated_claims.cypher`.
- **Newest unverified claims first, and intake below capacity (2026-10-01).** Never-attempted claims go newest-first (then retries by oldest attempt); the sweep verifies 20 per 6h (~80/day) and video learning extracts 3 claims per video, not 5. Before: ~83/day in, ~32/day verified oldest-first, so none of a week's 584 claims had been attempted.
- **Verification needs a cursor** — "no evidence" is a stable state, so `last_verify_attempt_at` is stamped **before** each attempt and selection orders on `COALESCE(last_verify_attempt_at, epoch) ASC`. Every `verify_one` return path names the `claim`, not just its id.
- **`unsourced_synthesis`** (retrieval-labelled, excluded from consolidation) is the type for the brain's own uncited reasoning; migrating a writer does not fix prior writes (`scripts/migrate_unsourced_gap_notes.cypher`). **A data fix and a code fix are separate deliverables.**
- **`verification: 'failed'` outranks the type in retrieval labels.** `label_claims` prefixes such a note `[FAILED VERIFICATION — <reason>. Its test results and code claims are false or unchecked; nothing in it was built, run successfully, or changed in the codebase]` (`failed_verification_label`). An `unsourced_synthesis` note that lists links says "the links it lists were not checked against its claims" instead of "cites no source" — a label the content visibly contradicts gets discounted. Backfill: `scripts/backfill_failed_verification.cypher`.
- **A claim's provenance is `synthesis_inference`** (an LLM extracted it). Until 2026-10-08 `store_claim` wrote `user_input`, the label for something a person stored, and recall shows it to the model. Existing claims: `scripts/fix_claim_provenance.cypher`. Nothing filters on provenance.
- **Every note's provenance is decided by who writes it** (`knowledge::effective_provenance`, 2026-10-08):
  - **`synthesis_inference`:** anything under a `ROUTE_CONTEXT` (a queue job, a chat turn, a sub-agent). It can't claim `user_input` even if a model passes it, because a model chose the words.
  - **`user_input`:** only an outside MCP client's `tools/call` with no route context of its own (`CLIENT_CALL`, set in `mcp/server.rs`), which may pass any value. `POST /api/notes` also writes it, explicitly.
  - **Unscoped brain code** defaults to `synthesis_inference`.
  - **`system_record`:** records the code builds, never words anyone chose (`store_episodic_note`: scheduler dispatches, claim evidence, code-version notes).
  - **Recall shows the label** to the model, and reads a missing one as `unrecorded`, never `user_input`.
  - **Why:** `store_note` used to assume `user_input`, and 11,513 machine-written notes said a person wrote them. Data fix: `scripts/fix_note_provenance.cypher`, which keeps the old value in `provenance_was`.
- **A claim must stand alone** (`claims::standalone_problems`, mechanical, so it holds for the local model that does all extraction). Extraction returns `about: [{name, what}]` for each claim, and three checks apply:
  - every `about` name must appear in the claim as whole words, and must be a name, not a vague noun ("video", "the system");
  - every bare "the/this/these/those + vague noun" ("the software") needs an `about` entry with that `what` that the claim names;
  - the claim may not open with a pronoun.
  
  A claim that fails gets one repair call told exactly what is wrong (`repair_claim`); one that still fails is **dropped and listed** in the tool result's `dropped` with its reasons. Stored claims carry `about`, `source_url` / `source_title` / `source_outlet` (`source_reference`), and the topic classifier reads the source title with the claim.
  
  The prompt rule that matters: when the source gives no name, say whose it is ("Paragon Solutions' spyware"), never "the spyware". On 8 real sources the local model stored 21 claims and dropped 2. The check doesn't catch a missing location ("AI agents were deployed" with no target named).
- **`rewrite-claims` restates stored claims so they stand alone** (`services/claim_rewrite.rs`, CLI):
  - **One cloud call per source note**, all of its claims at once, with the source text.
  - **An answer replaces a claim only if:**
    - it passes `standalone_problems`;
    - **and it loses no number or name**: `rewrite_losses` compares digit runs and each capitalised word part, after `canon` folds Unicode hyphens, quotes and spaces. That fold matters because gpt-oss writes "AP‑NORC" and "2026‑09‑28" with non-breaking hyphens.
  - **A failure** gets one targeted repair; a second failure keeps the text and sets `ambiguous` with `ambiguous_reason`.
  - **Typography-only changes** are not rewrites: `judge` compares lowercase letters and digits only, so "2024" vs "2024." or "64%" vs "64 %" counts as already standing alone, and the text is left as it was.
  - **The prompt forbids** spelling out acronyms or reformatting dates (`KEEP_AS_WRITTEN`); the guard would reject them. It also forbids additions, which the guard can't see.
  - **What a rewrite keeps:** id, status, attribution and evidence edges. The old text goes to `content_v1`; the claim is re-embedded and re-queued for topics.
  - **Resumable** on `standalone_checked_at`. A real run takes a snapshot first.
  - **`--dry-run --sample N`** samples across writers and writes nothing; **`--source-id`** targets one source.
  - **Not caught by any check:** verbs that soften meaning ("admitted" → "said"). The dry-run report is a person's check.
  - **After a run, run `eval-retrieval`.** Rewritten claims name their subjects, so they rise for queries about those subjects and can push an unchanged neighbour out of the top k (the 2026-10-09 run: recall@10 0.920 → 0.880 from one case at rank 10, MRR 0.757 → 0.780).
- **Where a claim was asserted is shown, not only stored.** `GET /api/notes/{id}` returns `asserted_in`: each `ASSERTED_IN` source note with `title` / `url` / `outlet`, read by `claims::source_reference` from the source's summary JSON (`title`, `url`, `site` or `channel`). Without one, the title is the first line (any heading level, ≤ 120 chars), and the URL is taken only from that line: a report's body links could be any of its sources. The note drawer renders it as **Asserted in** above provenance; a claim with no edge says so (25 of 4,510 on 2026-10-08).
- Chain-extracted claims get their `ASSERTED_IN` edge via `{{_prev.id}}` + `prev_result_raw`. The `claim` tool **echoes its input as `answer`** (safe to insert mid-chain). Standing schedules write `source_record` (not `semantic`) + a claim-extraction step + a `source_list` + a recency gate.

### Tool-integrated reasoning (`execute_code` + `sandbox` sidecar)

Lets a step *compute* its figures instead of hallucinating them; a wrong number becomes a traceback. **Execution never happens in the brain process** — `skills/exec.rs` is an HTTP client for the `sandbox` compose service. Isolation contract (in `docker-compose.yml`): **`sandbox-net` is `internal: true`** (no egress — the only real boundary), no `env_file` (no creds), no bind mounts, `read_only` root, `cap_drop: ALL`, `no-new-privileges`, `mem_limit: 2g`, `pids_limit: 128`, tmpfs `/tmp` `noexec`. **Do not put `sandbox` on `brain-internal` and do not add a `ports:` mapping.** Per-run limits in `sandbox/server.py`. **A failed run is a successful tool call** (`isError: false`, traceback in `stderr`) — a tool *error* would burn a retry and fail the owning Task. No state between calls; pass all input inline. `numpy`/`sympy`/`pandas` installed at build time (no run-time network). Routing: `computation` capability held by **`qwen2.5-coder:7b` alone** (`selection_rank 150`); `execute_code` in `general`/`self-analyst` allowlists. Behavioural half: `COMPUTATION RULE`.

**Rust goes through the same tool: `execute_code(language: "rust")` → the `rust-sandbox` service** (`RUST_SANDBOX_URL`). Takes `code` (a `main.rs`, `cargo run`) or `files` (a crate as path→content, default `cargo test`), plus `command` (`test`/`check`/`clippy`/`fmt`/`run`/`build`) and `include_ignored`; the result adds `tests_passed`/`tests_failed`/`compile_failed`, and for clippy `lint_findings` (one per diagnostic with a `-->` source location — clippy exits 0 on warnings, so the exit code says nothing). `fmt` runs `cargo fmt --check`: exit 1 + the diff on stdout, nothing rewritten. rust-analyzer is deliberately absent: it is a language server for a live editor session, and its one-shot `diagnostics` mode adds little over `check` + `clippy` on a single-request crate. A language is only offered in the schema when its sandbox URL is set, and `language` defaults to `python` so existing callers are unchanged. **Same isolation contract, two deliberate differences:** its `/work` tmpfs is **exec** (Rust must run the test binaries it compiles), and crates come from a **read-only cache fetched at image build** from `rust-sandbox/crates/Cargo.toml` with cargo run `--offline` — an uncached crate fails to resolve and the server appends the available list. The linker needs `TMPDIR`/`HOME` inside the writable scratch or it fails `Cannot create temporary file in ./: Read-only file system`. It runs as UID **10001**, not 1000, because `RLIMIT_NPROC` counts per real UID kernel-wide (the Python `sandbox` still shares UID 1000 with the host user). Built for `project-docs/RUST_FINETUNE_EXPERIMENT.md`. Full story: history § Tool-integrated reasoning.

  **So the predictor is the shape of the task, not its size.** Local is safe where there is no loop to close: one-shot synthesis (`schedule-author` drafts in a single pass) or a deterministic tool that *returns the answer* (`knowledge-worker`'s `recall_recent`). The model was right to say so: `search_codebase` is a **literal regex grep**, it was handed a prose question, and it returned an empty result naming nothing to try next. gpt-oss would have hit the identical wall. Two model-agnostic fixes, both the `recall_recent` count-then-drill doctrine applied again: (1) `search_codebase`'s zero-result path now re-probes each significant term (stopword-filtered, counts marked `N+` at the probe cap since an exact count would be a lie at the ceiling) and states plainly that it is literal, not semantic — "absence of the phrase is NOT absence of the code"; (2) `contexts/code-analyst.yaml` gained a LOCATE→READ→reason workflow, because the agent had `read_codebase_file` and never called it, and `reason` retrieves NOTES — which is how a doc's "lacks exponential backoff" claim got reported as a finding about the source. It also passes `file_pattern: ".rs"` now, after an unfiltered grep sent it to summarise CLAUDE.md instead of `queue.rs`. **When a local model underperforms, check what its tools actually returned before concluding the model is too small.** **Same class, also fixed:** `read_codebase_file` had `max_lines` (default 500, cap 2000) and a truncation marker but **no offset**, so everything past line 2000 of a 2790-line file was unreachable at any setting and an agent asked about logic at line ~1572 correctly reported it "not visible in the files examined". It now takes **`start_line`** (1-indexed, matching the `path:line` citations `search_codebase` emits), states the window it returned (`lines 2780-2784 of 2790`), and its continuation marker names the exact next call rather than the dead-end "use max_lines to read more". Past-the-end reads report the valid range instead of an empty result.

### Web Search: engine failover ladder + usage ledger

**★ Google syntax works on every engine, and `recency` replaces dates in queries (2026-10-02).** `skills/search_query.rs` parses Google's documented operators (`"phrase"`, `-word`, `-"phrase"`, `site:`, `-site:`, `filetype:`, `after:`, `before:`, `OR`, `(site:a OR site:b)` grouping) into a `QuerySpec`, and each engine renders what it reads: the Google family (SerpApi, Serper, CSE) gets the operators plus `tbs=qdr:`/`dateRestrict`; Google News gets `when:Nd`; Brave gets operators minus dates plus `freshness`; SearXNG gets operators but **no `time_range`** — it would drop every backend that cannot date-filter (Naver alone answered; news fell from 54 results to 2), so `searxng_items` enforces the window from each result's `publishedDate` and keeps undated ones; **Exa and Tavily read no operators**, so domains, dates, news and a short phrase become `includeDomains`/`excludeDomains`/`startPublishedDate`/`category`/`includeText`/`excludeText` (Exa) and `include_domains`/`exclude_domains`/`time_range`/`start_date`/`topic`/`exact_match` (Tavily). `search_web` takes `recency` (`day`/`week`/`month`/`year`) and `news: true`; a `source_list` becomes `site:` / include-domains on the spec. Why: Google News ranks by relevance, so the brief's "… today" queries returned months-old pages (0 of 8 current for world news on 10-02), while Exa news with a one-day window returned CNBC, Al Jazeera, France24 and Politico from that day; and `site:reuters.com` sent to Exa was searched as the word "site". **Write "latest …" plus `recency`, never a literal date** (a date over-constrains). The daily brief uses `engine: exa`, `recency: day`, `news: true`; the monitors carry `recency` matched to their cadence. An empty result still falls through the ladder, so a window too narrow for a niche query spends the keyed engines' quotas — keep daily monitors at `week`.


`search_web` walks an ordered **ladder** (`SEARCH_ENGINE_ORDER`, default `exa,tavily,serper,serpapi,google,searxng,brave`) until one answers **with results**.

- **Keyed engines are ordered by how they fail when spent:** monthly-refilling, no-card allowances first (Exa, then Tavily — Exa surfaced the primary source on 4 of 5 probe queries where Tavily returned blog posts, 2026-09-26), then Serper's one-time 2,500, then SerpApi (whose quota `google_news` needs), then Google CSE (closed to new customers, ends 2027-01-01) and Brave (card, no cap). All three new engines normalise to `{title, link, snippet, date}` (`normalize_tavily`/`_exa`/`_serper`), and `post_search` prefixes a spent allowance with "quota exhausted" because none of the vendors uses a 429 for it (Exa 402, Tavily 432/433, Serper "Not enough credits"). **Every key must be passed through in `docker-compose.yml`** — the brain has no `env_file`, so a key only in `.env` never reaches it (Brave and Google never had a pass-through before 2026-09-26).

- **★ `searxng` is the flagged last resort, not the lead (2026-10-06).** It always answers *something*, so leading with it starved the keyed engines (720 SearXNG searches vs 0 Tavily/Serper in a week), and with Google/Bing/DDG CAPTCHA-blocked its answers come from Naver, Seznam and Zapmeta: weaker relevance, undated, foreign-index pages. When it answers, the result leads with a `⚠ SEARXNG FALLBACK` banner naming each keyed engine passed over and why (and a date caveat when `recency` was asked), plus a WARN `Search answered by SearXNG fallback`. A caller that parses the result array must strip it with `web_result::strip_fallback_banner` (the claim verifier does, and records `searxng_fallback` on its output and evidence note). **Brave stays behind SearXNG**: card on file, no spend cap. The sidecar itself: self-hosted, no key/quota; `brain-internal` only, disabled `limiter` — do not add a `ports:` mapping without re-enabling it; keep `json` in `search.formats`). A **requested `engine:` is promoted, not made exclusive.** **Quota cooldown** (`QUOTA_COOLDOWN_HOURS` 6) moves an exhausted engine to the back, not out. Results normalised to `link`/`snippet`. Every attempt writes a `search_usage` row; `get_search_usage` reports per-engine + per-day.
- **★ Currents and Webz are NOT in the ladder — explicit `engine:` only (2026-10-06).** Measured on the brain's own schedule queries (intel monitor, Michigan brief, SLM watch, hardware tripwire; 7-day news): Currents ANDs every keyword and returned **0** for all four; Webz returned QAnon-style, partisan and off-topic pages (Michigan politics → Bangladesh and Nigeria), **no result from any SourceList**, and `domain_rank:<1000` left 0. Because a non-empty answer ends the ladder, leading with them displaced Exa — which answered the same intel query with AP, NBC, ABC and NPR. They had led news searches for about an hour before this was measured and reverted. Still usable when named: Currents for short specific queries, Webz restricted by `site:`/`source_list`. Rules that still apply when they run: Currents takes one include/exclude domain and ≤ 8-day windows clamped to 7 (`engine_unsupported`, `currents_params`); Webz ≤ 31 days clamped to 30, 5 results (prepaid ~$0.01/result). **Measure an engine on the brain's real queries, classed by SourceList, before putting it in the ladder.** The same holds for a SourceList: `national-security` and `semiconductors` (2026-10-06) were each run against their schedule's real queries, current setup vs proposed, before any schedule used them. Engine errors pass through `redact` (Webz echoes its token).
- **Search-results pages are dropped from every engine's answer, before it is counted** (`drop_search_pages`, check in `services/web_result.rs::is_search_page`). `ecosia.org/search?q=…`-style pages restate the query in their snippet; an answer made only of them counts as empty and the ladder moves on. A `search` path segment counts only with a query string or a further segment after it (`/wiki/Search` is an article). The claim verifier additionally drops results whose snippet contains the whole claim (`drop_echo_results`).
- **An engine with no credentials is dropped from the ladder outright, not demoted** (`is_engine_configured` + `retain_configured` in `engine_ladder`). Unlike a spent quota (which recovers overnight, so demote), a missing key never fixes itself at runtime, and it fails `not_configured` on *every* call — the 2026-09-08 GDELT session put `engine: google` on each search with no `GOOGLE_API_KEY`, wasting the first rung and a WARN line on every one and helping exhaust the 8-round chat budget twice. `searxng` needs no key (always kept); `google` needs key **and** CX; `serpapi`/`google_news` share one key; `brave` needs a key. Never empties the ladder: if nothing is configured the original is kept so the caller still gets a real per-engine error. An unknown engine name is assumed configured. Guards: `unconfigured_engines_are_dropped_from_the_ladder` + siblings in `search.rs` tests.
- **Zero results is not an answer** — a rung returning `200` + empty falls through to the next; if *all* rungs come back empty, return `[]` (erroring would burn retries). Fall-through logged at WARN.
- **SerpApi signals failure as HTTP 200 + `{"error":…}`, not a 4xx/5xx** (quota, rate, "couldn't get valid results"). `search_serpapi`/`search_serpapi_news` check the `error` field and return it as a real failure (raw message → `classify_search_error` → the ladder WARNs, records the right `error_kind`, and demotes on quota). Before this fix (2026-09-08) that response was read as `success` with 0 results and the ladder fell through to SearXNG **silently** — a real SerpApi outage looked like success in the logs and over-counted `serpapi` in the ledger. A genuinely-empty result with no `error` field is still a real empty (falls through with the zero-results WARN, no cooldown). **`unresponsive_engines` in the JSON is the diagnostic** (distinguishes "cannot connect" from "connected and refused"); `scripts/searxng_engine_health.py` probes both evergreen and fresh query shapes. **Never probe a single engine with `&engines=<name>`** (silent fallback to the default set); attribute by each result's own `engine` field. A relevance failure cannot be caught by a count.
- **News: `engine: "google_news"`** (`search_serpapi_news`, SerpApi `engine=google_news`). SerpApi free tier is **250/month** (not 100); `serpapi`+`google_news` share one account (ladder demotes both when either is exhausted). No `source_list` on Google News steps. `google_news` is **not** in the default ladder. **Query rewriting was investigated and rejected** (null result — the queries were never the problem; the blocked engines were). **Quota exhaustion alerts** (`is_quota_exhausted_error`, deduped `:AgentNotification` once/tool/24h).

Full story (the four outages — DNS/empty results, bot-blocks, junk results — and the query-rewriting A/B): history § Web Search.

### Media Learning (watch & summarize videos)

**★ A LIVE broadcast is rejected up front, and `MEDIA_MAX_DURATION_SECS` cannot do it for you.** `fetch_via_ytdlp` bails on `meta.is_live` **before** the caption path. Two independent reasons the old cost guard never fired: it lives on the *no-captions* branch only (a live stream with auto-captions skips it entirely), and yt-dlp reports `duration: null` for a live stream, which parses to `0` — so `0 > 10800` is false. A live broadcast also has no end, so `ingest_media`'s map-reduce has no finite transcript and the job simply hangs. `was_live` (a finished stream, now a normal VOD with a real duration) is deliberately NOT treated as live. Observed 2026-09-11: a `watch video:` task on a broadcasting stream held one of the two local job slots for **3 hours across 29 attempts**, burning zero LLM calls and recording no error.

**`poll_media_sources` filters `is_live` at DISCOVERY too, so a live stream never becomes a Task** — no chain, no retry cycle, no failed owning Task. The probe is deliberately no longer gated on `MEDIA_MAX_DURATION_SECS > 0`, because a live broadcast is unbounded whatever cap is configured. **It records NO dedup `:Media` node**, unlike the over-length path: a video's duration never changes, so `skipped_too_long` is correctly permanent, but "live" is TEMPORARY — the broadcast ends and YouTube republishes it as an ordinary video. Motivating source: `c-span`, the highest-volume watchlist entry (25 tasks in 7 days) and the one that broadcasts live.

**A scheduled premiere is skipped like a live stream.** yt-dlp refuses an upcoming event outright ("This live event will begin in N hours"), so the poll's duration probe fails; `media::is_not_yet_available` recognises that and the poll skips it with no dedup node (it is picked up after it airs), and `parse_meta` treats `live_status: is_upcoming` as live. Two premieres dead-lettered in the week to 2026-10-01.

**Every video links to its watchlist source by channel id.** The poll's `watch video:` task carries only the URL, so the source name never reached `ingest_media` and **no video had a `FROM_SOURCE` edge** (0 of 1,089) until 2026-10-01. `ingest_media` now falls back to `link_media_by_channel` (a YouTube `MediaSource.ref` is the channel id); `scripts/backfill_media_from_source.cypher` linked the existing 1,089.

### Context Profiles

Also note `run_agent(agent:"auto")` is a **token-overlap** matcher: "how many **agents**" matches `researcher` on the word alone, so a meta-question must never be left to auto-select.
- **The default profile is excluded from `auto_assign` candidates** (it is the fallback; matching it explicitly would shadow a real specialist), and `delete_profile` protects it as well as `general`.
- **`delegate` is chat-loop only and is NEVER in the MCP tool registry.** A profile used for `MCP_TOOL_PROFILE` must therefore include **`run_agent`** (the registered equivalent) or an MCP client gets the allowlist with no dispatch path at all — strictly worse than the full registry. Both vars point at the front door, so a connecting client sees 7 tools instead of ~42.
- **★ A front-door prompt is a SIZE BUDGET on a small local model.** Same model, same tools, same question: at 2332 chars E4B delegates; at 6801 it emits prose and refuses. The added bytes were `general.yaml`'s ABSENCE / TOOL-RESULT / CITATION rules — all of which say *don't overclaim* — and a 4B model over-applies them into the exact "I cannot determine this" they exist to prevent. Those rules are persuasive narratives written for a large model. Keep a local profile's prompt near 2-3k chars (the front door is at 4.0k after the `ABOUT THE BRAIN ITSELF` rule and still delegates — re-measure if it grows again), write rules as terse imperatives, and include an explicit floor ("When in doubt, DELEGATE; never answer 'I cannot determine this' without having called delegate at least once this turn"). Narrative rationale belongs in history, never in a local model's prompt.

## Critical Dev Notes

> Long root-cause narratives for the starred rules live verbatim in **`project-docs/engineering-history.md`** (§ *Critical Dev Notes*).

**LlmConfig:** `base_url` is `Option<String>`. Default model `"qwen3.5:4b"`. Tests: `config.base_url.as_deref()`.

**Parse the FIRST complete JSON object, never first-`{`-to-last-`}`.** If no candidate parses, it retries once with stray backslashes escaped inside strings (`escape_stray_backslashes`): a `$\approx$` in a `reason` answer failed the whole parse on 2026-09-30, and the raw JSON became a Task goal. `services::llm::first_json_object(text, must_have)` stops after one value and requires the named keys, so a repeated answer, trailing prose or a fence cannot break it. The old slice spanned two objects when a model wrote its ```json answer twice (2026-09-26), the parse failed, and the fenced raw reply was stored as a monitor report. `reason` (both paths), audit, counter-arguments, adversarial review, `parse_adversarial_robustness` and the constructor's plan parser all use it.

**Structured LLM output:** for strict JSON, call `LlmProvider::generate_json(prompt, system, required_keys, max_retries)` (self-correcting re-prompt loop) rather than hand-rolling `generate` + `extract_json` + `from_str().unwrap_or_else`. `extract_json` picks the **earliest-opening** delimiter; pass `&[]` for `required_keys` to accept any valid JSON.

**★ Pick the local model by VRAM residency, not leaderboard.** Residency is a cliff, not a curve: every model that fits generates at 67–125 tok/s, one that doesn't (`gemma4:latest`, 9.86 GB on an 8 GB card) at ~26. Models don't co-reside here — a swap is a replacement; unload the outgoing model (`keep_alive: 0`). **`granite4:latest`** is the local model (`OLLAMA_LOCAL_MODEL` in compose; already `selection_rank 120`), 18× faster than `gemma4` in production. Benchmark the **structured** path too (a fast model can emit unparseable JSON), and beware thinking models — `qwen3.5:4b` (the stale `DEFAULT_MODEL` in `llm.rs`) emits into `thinking` and returns an **empty** `response`. Output length is a cost, not a quality signal. Full tables: history.

**★ The local model has its own timeout.** `OLLAMA_LOCAL_TIMEOUT_SECS` (default **600**) applies to the local background config alone (built in `brain_core.rs`); cloud calls keep the 120s default. It's burstiness, not average load — `poll_media_sources` fans ~30 videos out at once; at 30–75 calls/hour latency climbs to 120s and every call clips. Killing a call at 120s throws away spent compute *and* the chain built on it. Not the cause: concurrency (Ollama batches) or Ollama being down. Full incident (the `0426218` fan-out move): history.

**★ llama.cpp backend for background jobs.** The generation backend for `provider_hint:"ollama"` steps is env-selectable via `LOCAL_LLM_BACKEND` (`ollama` | `llamacpp`); the switch is in `services/llm.rs::build_local_llm_config`, used by both `brain_core.rs` and `scheduler.rs`. `LlmProviderType::LlamaCpp` reuses the existing OpenAI-compatible provider (`openai_compat.rs`) — llama.cpp's `llama-server` speaks the same `/v1/chat/completions` wire format as Ollama Cloud. **Load-bearing facts:** (1) **Embeddings never move** — `build_local_llm_config` pins `embed_base_url` to `OLLAMA_LOCAL_URL` no matter the backend, because a single-model `llama-server` doesn't serve `/api/embeddings`; host Ollama stays up for bge-m3. (2) `keep_alive`/`num_ctx` are Ollama-native and **ignored** by the llama.cpp provider — set context/offload as `llama-server` launch flags in the compose `command:` (`-c`, `-ngl`, `--flash-attn`, `--cache-type-k/v`), not per-request. (3) `USE_LOCAL_LLM` routing is backend-agnostic (keyed on the flag, not the provider type), so a llama.cpp local route is still `is_local_route=true` and never falls back to cloud. (4) **The local model is a thinking model** — background steps that parse JSON need thinking OFF or the reasoning leaks into `content` and no JSON is emitted. **The flag is model-specific**: Qwen3 honors `--reasoning-budget 0`; **Gemma 4 IGNORES it and needs `--reasoning off`** (verified 2026-09-10 — E4B leaked its whole thought process until switched). Current production model is **Gemma-4-E4B** (`--reasoning off`), chosen over Qwen3-8B because it's fully resident at ~3.3 GB (weights) vs 6.0 GB and ~14% faster — see the residency note below. Provider variant + `build_local_llm_config` are covered by the lib tests; scope of the switch is background jobs only — human `/chat` stays on Ollama-Cloud.

**★ The llama.cpp CUDA image must match the host driver (`llamacpp/Dockerfile`).** The GPU is an RTX 3060 Ti (8 GB, sm_86); the host driver is **535 / CUDA 12.2**. The upstream prebuilt `ghcr.io/ggml-org/llama.cpp:server-cuda` ships **CUDA 12.8** and will NOT run on this driver: its bundled forward-compat stub (`libcuda.so.570`) aborts CUDA init on a GeForce (`forward compatibility was attempted on non supported HW` → silent CPU fallback), and even with the stub removed the 12.8 cubins fail to load (`CUDA error: device kernel image is invalid`). So the sidecar is **built from source against CUDA 12.2** targeting sm_86. Two build gotchas the Dockerfile encodes: link with `-Wl,--allow-shlib-undefined` (libggml-cuda references CUDA Driver-API symbols the devel image keeps in `lib64/stubs`; they resolve at runtime when cudart loads the injected `libcuda.so.1`), and enable `-DLLAMA_OPENSSL=ON` + `libssl-dev`/`libssl3` (b10900's `-hf` downloader uses a native TLS client — without it, `HTTPS is not supported` and it can only load an already-cached GGUF). The production model **Gemma-4-E4B Q4_K_M sits ~3.3 GB** on the GPU (4.6 GB with the 16k KV cache) alongside bge-m3 and the whisper sidecar, leaving ~2.8 GB free. (It replaced Qwen3-8B at 6.0 GB / 70 tok/s: E4B is ~14% faster and half the VRAM — Gemma-3-**12B does not fit resident** on 8 GB, spilling to ~21 tok/s.) Full rationale in the Dockerfile header; benchmark detail in the memory note `llamacpp-switch`.

**A `reqwest` failure says what went wrong.** `describe_reqwest` (`llm_providers/mod.rs`) prefixes the kind (`operation timed out:` / `connection refused:`) — the "why" lives in `source()`, which `Display` drops — and appends the full cause chain. The prefix survives job-`error` truncation and matches the phrases `classify_unavailable` uses.

**Every failed LLM call records an `error_kind`.** `SharedLlm::generate`'s per-call `record_model_usage` used to hardcode `None`; now every attempt (primary and each fallback rung) goes through `run_and_record`, whose `failure_kind` reuses `classify_unavailable` and falls back to `"other"`.

**★ A cloud LLM that cannot answer walks a fallback chain; one that answers and refuses does not.** `classify_unavailable` (`services/shared_llm.rs`) qualifies four kinds: `rate_limited`, `subscription_required` (403 "requires a subscription"), `transport` (DNS/refused/TLS/client timeout — never reached the provider), `server_error` (5xx). Anything else propagates (falling back on a 400/401 just gets a worse rejection). `is_server_error` matches canonical reason phrases, not bare numbers (`contains("500")` fires on token counts). Fallback is guarded by `!is_local_route` (a local model never retries against itself) and the chain order comes from `build_fallback_chain`: a **capability-selected** cloud route (e.g. a `reasoning` step routed to `gemini-2.5-flash`) falls back to the **active config first** — the free Ollama-Cloud model, which does not share the selected model's quota, i.e. "what we were doing before" — and only then to local; a route that WAS the active config skips straight to local. This is why routing reasoning at `gemini-2.5-flash` and hitting its 1500 RPD ceiling degrades to `gpt-oss:120b-cloud`, not to weak local granite4. Each rung (primary included) records its own `model_usage` row via `run_and_record`. Full incident (the lost off-grid report): history.

The **chat path has its own ladder** (`chat_fallback_ladder` in `models.yaml`, walked by `run_one_attempt` in `clients/chat/turn.rs`) — it turns on "did the turn produce output", not the error class, and runs Ollama Cloud → Mistral → OpenRouter `:free` → local (the may_train rungs since 2026-10-10; OpenRouter's 50/day is metered by the budget, and the policy refuses it for sub-agents). **A model that fails mid-turn hands its work over (2026-09-26).** If it ran only read-only tools (`call_is_read_only`: not a `WRITE_TOOLS` member, no `manage_*`/`ingest_*`/… prefix, `http_request` GET/HEAD, `mcp_call` to a fetch/search/list tool; `delegate` counts as read-only because chat sub-agents cannot write), `run_one_attempt` returns `Interrupted` and the next rung gets a `WORK ALREADY DONE THIS TURN` block with each call and its result, told not to repeat them. A turn that ran a **write** still owns the turn and reports the error, so a write is never repeated by a second model. Before this, any error after the first tool call ended the turn: a `gemini-3.6-flash` 503 on the round after a delegate returned nothing. **A failed voice pass sends the worker's own answer** with a `⚠ voice model … failed` note (`voice_fallback`) instead of discarding it. **Chat calls now record `error_kind`** (`shared_llm::failure_kind_of`), and a `server_error` benches the model for 60 s in the budget, so the next turn skips a model that just returned a 503. **A profile may declare `fallback_models:`**, walked after its pin and before the global ladder (ahead of the chat default when the pin is refused); the front door steps `gemini-3.6-flash → gemini-3.8-flash → gemini-2.5-flash → Ollama Cloud → local`. Guards: `a_failure_after_read_only_tools_hands_the_work_over`, `a_failure_after_a_write_keeps_the_turn_and_its_error`, `every_profile_fallback_model_is_in_the_catalog`. **`run_bounded_loop` (the sub-agent loop behind `run_agent`/`delegate`) walks that same ladder**, so a transient 500 on a sub-agent's primary model degrades to the next rung instead of surfacing the raw error as the whole delegated answer — and every rung it walks is admitted by the routing policy for the sub-agent's purpose and data class (OpenRouter's rung is refused for sub-agents by its 50/day limit). Before this it dispatched a single provider loop with no fallback and failed a delegated task on a provider blip.

**A tool name is owned by the first skill that claims it.** Dispatch is first-match, and the built-ins register before `DynamicSkill`, so a DynamicTool reusing a built-in's name never runs. It was still listed and, worse, validated against: the step-schema snapshot was last-wins, so an obsolete 09-07 dynamic `ingest_api` (`spec_url` required) made the audit mark the brain-api-sync schedule broken. The snapshot is now first-wins with a startup WARN per duplicate, `manage_dynamic_tool define` refuses a built-in's name, and the stray tool is removed.

**Skill registration:** push the skill ONCE onto the `skills` list in `BrainCore::build_skills`; the registry (`tools/list`) and the handler (`tools/call`) each get an `Arc` of that same instance (`impl Skill for Arc<T>` in the protocol crate). Before 2026-10-02 every skill was constructed twice, one copy per side, and the copies had drifted (the registry's `MediaSkill` had no knowledge store). Order matters: dispatch is first-match, so `DynamicSkill` stays last.

**★ Embedding fails on LENGTH, and the limit is TOKENS — the old "`500 … NaN` for certain strings" diagnosis was wrong.** Probed against the live `bge-m3` 2026-09-12: emoji, control chars, zero-width joiners, CJK, punctuation and whitespace-only input all embed cleanly at 1024 dims. Two real failure modes: **empty input returns HTTP 200 with a ZERO-LENGTH vector** (worse than an error — it flows into `db.index.vector.queryNodes` as a silent no-op reading as "nothing is similar"), and **over-length input 500s**. The ceiling is ~3,200 tokens, which is **~10,327 chars of prose but only ~5,819 of dense JSON/URL content** — so a character cap cannot be right for both, and one set from the prose measurement still 500'd on 3 of the 4 notes it was meant to repair. `prepare_embed_input` (`llm_providers/mod.rs`) rejects empty and caps at **4,000 chars** on a char boundary (compile-time `const _: () = assert!` pins it below the measured dense ceiling); `embed_with_backoff` halves and retries up to 3× on a length-shaped failure only — a missing key is not retried.

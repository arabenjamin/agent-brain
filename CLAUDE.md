# CLAUDE.md

Guidance for working with the Agent Brain codebase.
This repository is forked from the original [Agent Api]("https://github.com/arabenjamin/agent-api") and has diverged significantly in architecture, design, and implementation. Though there are still some leftovers from the original codebase, the majority of the code has been rewritten to support a persistent, self-improving autonomous agent brain with a Neo4j knowledge graph and a pluggable LLM backend.

## Project Overview

Autonomous Agent Brain — A persistent, self-improving MCP server in Rust backed by a Neo4j knowledge graph. Manages long-term memory with hybrid vector+BM25 RAG, executes background jobs in a durable priority queue, reasons over stored knowledge, and runs an autonomous background scheduler that continuously improves itself by dispatching pending tasks as job chains.

## Tech Stack

- **Language:** Rust (Tokio async runtime, Edition 2024)
- **Protocol:** Model Context Protocol (MCP) via stdio or HTTP transport
- **Web Framework:** Axum (HTTP transport with SSE streaming)
- **Database:** Neo4j via `neo4rs` driver
- **AI Model:** Pluggable — Ollama (local), Ollama Cloud, Anthropic, or Gemini

## CLI Commands

```bash
# Run as MCP server (default - stdio transport)
cargo run -- serve
cargo run                      # Same as above

# Run as MCP server with HTTP transport
cargo run -- serve --transport http                           # HTTP on localhost:3000
cargo run -- serve --transport http --bind 0.0.0.0:8080       # Custom bind address
cargo run -- serve --transport http --api-key my-secret-key   # With API key auth

# Initialize database schema
cargo run -- init-db
```

| `LLAMACPP_URL` | `http://localhost:8080` | `llama-server` OpenAI-compatible endpoint, used only when `LOCAL_LLM_BACKEND=llamacpp`. **Compose sets `http://llamacpp:8080`** (the sidecar service). | `OLLAMA_LOCAL_MODEL` | `gemma4:latest` (**compose sets `granite4:latest`**) | Model used exclusively for all background/scheduled jobs. | `OLLAMA_NUM_CTX` | `16384` | Context window for **host-Ollama generation** (`options.num_ctx`). Measured 2026-09-11: 103 of 874 `reason` calls over 30 days came back with `tokens_in` sitting exactly on 4096 (granite4 58, gemma4 45; the llama.cpp and cloud paths zero) — answered from a clipped prompt, no error, no marker. ## Architecture Summary

See `project-docs/architecture_context.md` for skill registry table, initialization order, and mechanics. See `project-docs/STATUS.md` for current tool counts and feature status.

**Nodes:**
- `Task` - High-level goals with `id`, `goal`, `context`, `success_criteria` (measurable definition of done — used by evaluator step), `status` (created/in_progress/completed/failed/blocked)
- `Note` - Stored text memories with optional vector `embedding`, `access_count`, `last_accessed_at`, `note_type` (`semantic`/`episodic`/`reflection`/`consolidated`/`outcome`/`inference`/`claim`/`source_record`/`news`), `next_review_at`, `review_interval_days`, `source_context`, `event_at`
- `Procedure` - Named multi-step workflows with `id`, `name`, `description`, `steps` (JSON array), `created_at`
- `WorkingMemory` - Session-scoped scratchpad entries with `id`, `session_id`, `content`, `role`, `turn_index`, `created_at`
- `Entity` - Named entities extracted from notes with `id`, `name` (unique, lowercased), `entity_type`, `created_at`
- `DynamicTool` - Runtime-defined MCP tools with `id`, `name` (unique), `description`, `input_schema` (JSON), `created_at`
- `AgentJob` - Background job record with `id`, `tool_name`, `args_json`, `priority` (0-3), `status` (queued/running/completed/failed/dead/parked/cancelled), `attempt_count`, `max_attempts`, `result_json`, `error`, timestamps, `session_id`, `parent_job_id`
- `ModelSpec` - Registered LLM models with capabilities, cost, and usage stats
- `ToolDef` / `ContextProfile` / `ModelDef` - **Self-model meta-graph** (Phase 0b of the Agent Constructor plan). Generated by introspection in `services/self_model.rs` at the end of every `build_skills()` — never hand-edit: the tool registry, `contexts/*.yaml`, and the DuckDB model catalog are the sources of truth, and stale nodes are deleted on each sync. `(:ContextProfile)-[:ALLOWS]->(:ToolDef)` edges mirror profile tool allowlists (`allows_all: true` when the profile has no allowlist). Chains/schedules are not duplicated here — `(:SchedulerChain)`/`(:ScheduledTask)` already are the graph representation.
- `BrainVersion` - **Singleton `{id:'current'}`** recording the commit this process is running (`sha`, `subject`, `branch`, `dirty`, `seen_at`, `deployed_at`). Written by `sync_code_version()` in `services/self_model.rs`, right after the meta-graph sync. When the sha differs from the stored one it also writes ONE episodic note (`source_context: "code_version <sha>"`) listing the changed files; an unchanged sha is a no-op, so restarts cost nothing.

  This replaced a `post-commit` → `scripts/self_update.py` round-trip (deleted 2026-08-10). That script re-derived over HTTP what the process already knows, and got it wrong: it parsed `analyze_own_structure`'s **Markdown** output as JSON inside a bare `except: pass`, printing `tools at runtime: 0` on every commit since March, and it indexed `result[0]` on a dict. It also fired on `git commit` — before the rebuild it triggered had finished — so the note described code that was not yet running, and it only ever covered a local `git commit` (not `docker compose restart`, CI, or a pull on another machine). Reading HEAD in-process at startup reports **what is actually loaded**. The hook is now just `docker compose up -d --build`.

**Relationships:**
- `(:Note)-[:RELATES_TO {similarity: float}]->(:Note)` — auto-created when similarity ≥ 0.75
- `(:Note)-[:SUMMARIZED_BY]->(:Note)` — source notes pointing to their consolidated summary
- `(:Note)-[:REFLECTS_ON]->(:Task)` — reflection/outcome notes linked to the task they critique
- `(:Note)-[:PART_OF]->(:Note)` — semantic chunk linked to its parent note
- `(:Note)-[:MENTIONS {count}]->(:Entity)` — entity mentions extracted from note content
- `(:Note {note_type:'inference'})-[:DERIVED_FROM]->(:Note)` — inference notes citing their sources
- `(:Task)-[:SUBTASK_OF]->(:Task)` — sub-tasks created by `decompose_goal`
- `(:Task)-[:DEPENDS_ON]->(:Task)` — dependency edges for task ordering
- `(:DynamicTool)-[:USES]->(:Procedure)` — links a dynamic tool to its step definition
- `(:AgentSpec)-[:CONSTRUCTED_FOR]->(:Task)` — a constructed agent linked to the task it was dispatched for
- `(:AgentSpec)-[:PERFORMED {score, passed, at}]->(:Task)` — graded outcome written by the queue's evaluator hook; the constructor's reuse-before-construct prefers specs with avg score ≥ 3.5
- `(:ApiContext)-[:EXPOSES]->(:ApiEndpoint)` — endpoints ingested by `ingest_api` (see below). `:ApiEndpoint {api_name, method, path, summary, operation_id, parameters, security, tags}` MERGE'd on `(api_name, method, path)`, so re-ingest updates in place.

### Native REST API ingestion (`ingest_api`)

`ingest_api` in `HttpSkill` (`skills/http.rs`) ingests a REST API's endpoints from **one of three sources** (pass exactly one) and stores each operation as an `(:ApiEndpoint)` under an `(:ApiContext)` via `[:EXPOSES]`. This is the properly-resurrected agent-api "spec → endpoint graph" idea (the old `ingest_openapi` was a doc-comment ghost; the code was never ported).
- **`spec_url`** — a direct OpenAPI 3.x / Swagger 2.0 doc (JSON **or** YAML).
- **`docs_url`** — an HTML docs page. Deterministically detects the linked spec: scans the page, then its referenced `.js` (Swagger UI keeps the `url:` in `swagger-initializer.js`); when a page advertises several specs (the Swagger demo dropdown) it **prefers one on the same host as the page**; unwraps `host=https://…` map entries. If a spec is found it ingests via the spec path (`source: html_spec`). If **no** spec is linked, it **falls back to LLM extraction** from the page text (`html_to_text` → `generate_json`, `source: html_llm`) — lower confidence (verify before relying on it), used only after deterministic detection fails. Needs the injected `Arc<dyn LlmProvider>` (unmetered `SharedLlm`); absent it, a clear error.
- **`codebase_path`** — a local dir searched (bounded, skips `node_modules`/`target`/…) for an existing spec file (`openapi`/`swagger` `.json`/`.yaml`, `api-docs.json`) → parse it (`codebase_spec`). No spec file → **build-from-routes**: `find_route_files` scores source files by route-marker density (axum/actix, FastAPI/Flask, Express, Spring, gin/echo), feeds a bounded corpus of the top files to the LLM, which returns the endpoint list (`source: codebase_generated`, lower confidence — it merges router prefixes and infers params from signatures, but reads registrations not a contract).

Spec-based parsing is a `serde_json::Value` walk — **no LLM**, so no truncation/hallucination. Every operation → method, path, summary, operationId, merged path+operation parameters, security scheme names, tags. base_url resolves 3.x `servers[0].url` (absolute or relative-to-origin) → 2.0 `schemes[0]://host+basePath` → the spec URL's origin. The `(:ApiContext)` records provenance: `source` (`openapi_spec`/`html_spec`/`codebase_spec` are deterministic; `html_llm`/`codebase_generated` are LLM-derived, lower confidence) + `discovered_from`. Endpoints MERGE on `(api_name, method, path)` (idempotent). Persistence (shared by spec and LLM paths, `persist_endpoints`) uses the atomic `UNWIND $endpoints` + `RETURN count` read-back (the dynamic-tool-fix lesson: one query, no cross-connection MATCH, verify the write landed). Fetch/file-read run **in the brain process** (has egress/FS), never the sandbox. Query results with `neo4j_query`. Parser/detection tests: `ingest_api_tests`. All four ingestion routes (spec URL, HTML docs, codebase spec-file, codebase build-from-routes) are implemented; the two LLM-derived sources are labelled lower-confidence rather than deferred. **`prune: true`** turns re-ingest into a true sync: after the upsert it deletes endpoints of the same API not written in this run (older `updated_at`), so a removed route disappears — the result adds `endpoints_pruned`. **The brain keeps its OWN API doc current with it**: `schedules/brain-api-sync.yaml` (weekly) runs `ingest_api(codebase_path=".../crates/app/src/mcp", name="agent-brain", prune=true)` on unmetered ollama-cloud — the brain publishes no OpenAPI spec, so this build-from-routes ingest over its Axum route table IS its self-documentation (`ApiContext` `agent-brain`, ~48 endpoints); step 2 banks a dated endpoint/prune-count record (`source_context: brain_api_sync`). Point the same tool + a schedule at any other service on the network (a spec URL, a Swagger UI page, or a repo) to give the brain a queryable map of that API too.

**Autonomous discovery (`api-scout`).** `contexts/api-scout.yaml` is a spawnable profile (search_web + http_request + ingest_api + notify_user) that scouts the web for free public REST APIs in the brain's interest areas and **ingests the keyless ones** (a spec reachable without an account) while **`notify_user`-flagging the key-gated ones** for a human to supply a key — it never signs up or invents a key. `schedules/api-scout.yaml` drives it weekly via a single `run_agent(agent="api-scout")` step and is **seeded disabled** (`enabled: false`) for review; turn it on with a Cypher `SET s.enabled=true, s.next_run_at=datetime()`. It is the discovery half of the API toolchain; `api-integrator` is the build-a-client half. Requires `SUBAGENT_ENABLED=true`.

**Stdio Transport (Default)**
- Standard input/output for local CLI usage
- Best for MCP clients like Claude Desktop that spawn the server as subprocess

**HTTP Transport**

## Architecture: subsystem rules

> Each subsystem below is stated as its **operative rules only**. The full narrative — root causes, measurements, and the failures that motivated each rule — lives verbatim in **`project-docs/engineering-history.md`** (§ *Architecture & subsystem deep-dives*). Read the matching section there before changing one of these; nearly every rule marks a failure mode the codebase re-learns whenever the reasoning is dropped.

### Self-Improvement Loop

`SchedulerService` background task: lists `status=created` Tasks → `goal_to_steps()` → `enqueue_chain()` → marks `in_progress`. After `idle_sleep_after_ticks` (3) idle ticks → `enter_sleep()` (consolidate → prune → snapshot). `notify_activity()` resets the idle count. `QueueService` coordinator runs jobs serially per provider semaphore, retries transient failures, unparks dependents on success.

- **★ Crash recovery respects `max_attempts` — a hung job is NOT immortal.** `reset_running_agent_jobs` used to flip every `running` job back to `queued` unconditionally, which made `max_attempts` meaningless across a restart: a job that **hangs** is never marked failed, so it is still `running` at the next startup and gets resurrected, forever. It now dead-letters jobs already at their cap (with a `j.error` saying so) and requeues only those with attempts left; the count it returns is the REQUEUED count, dead ones logged at WARN. Observed 2026-09-11: an `ingest_media` job on a live stream reached **attempt 29 against a cap of 3**, revived by each restart during a day of rebuilds. **Not media-specific** — any job that hangs rather than failing hits this, which is why the fix is in recovery, not in a per-tool timeout.
- **Dead-job meta-learning:** on retry exhaustion, store a reflection note and — for non-infra tools (`should_meta_learn`) — enqueue an Analyze→Hypothesize→Test→Integrate chain. Guards: `is_transient_infra_error` (skip for quota/rate/timeout/5xx) and `recently_meta_learned` (≤ once/tool/24h).
- **Chain-death task attribution:** `enqueue_chain_owned(steps, session_id, Some(&task_id))` stamps `__owner_task_id` on every step; on step death the coordinator calls `fail_task_with_reason(task_id, reason)`, guarded to `status IN ['created','in_progress']`. `enqueue_chain` is the no-owner wrapper (chat/bedtime/meta-learning).

### Evaluator Loop (Generator-Evaluator)

A Task with `success_criteria` gets a `reflect_on_work` evaluator step appended by `goal_to_steps()`. It parses a `Score: N/5` line; `< min_score` (default 3.5) → mark task `failed` + create a new Task with the critique in `context`. **Retry cap 3** (`handle_evaluator_requeue` counts `"RETRY —"`). **Unparseable output = pass** (`parse_evaluator_score` → `None`; do *not* fabricate a 3.0 and do not grade the AgentSpec). `ChainStep`: `is_evaluator`/`min_score`/`evaluator_task_id`; args `__evaluator_min_score`/`__evaluator_task_id`. A `:SchedulerChain` may carry `evaluation_rubric` to override the goal text. Full story: history § Evaluator Loop.

### Adversarial Critic (pre-flight plan review)

A Task with `success_criteria` also gets an `adversarial_plan_review` step **prepended**. `overall_robustness < min_robustness` (default 2.5) → cancel downstream + `handle_adversarial_requeue()` (mark failed, new Task with critique). **Abort cap 3** (`"ADVERSARIAL ABORT"`). Skipped when: no `success_criteria`, chain `no_adversarial: true`, or context already has `"ADVERSARIAL ABORT"`. `ChainStep`: `is_adversarial`/`n_hypotheses`/`min_robustness`/`adversarial_task_id`. `parse_adversarial_robustness()` defaults 3.0. Also callable directly (KnowledgeSkill); each run stores a `semantic` note `source_context: "adversarial_review"`. Full story: history § Adversarial Critic.

### Externalized Agent Chains

Scheduler routing chains are `chains/*.yaml` seeded as `(:SchedulerChain)` by `init-db` and force-refreshed on the first tick after every startup. `goal_to_steps()` queries Neo4j, falls back to `build_diagnosis_chain()`.

**Chain YAML schema:** `name` (MERGE key), `pattern` (primary CONTAINS), `patterns: [...]` (OR), `priority` (lower = matched first; default chain 9999), `no_evaluator`, `no_adversarial`, `evaluation_rubric`, `steps: [...]`.

- **Matching is plain CONTAINS; priority is the only tiebreak.** A broad substring pattern silently hijacks a specific one if it sorts first — put specific prefixes at low priority numbers, and check no broader pattern outranks a new chain.
- **Template vars** in step `arguments`: `{{goal}}`, `{{goal_topic}}`, `{{task_id}}`, `{{date}}` (local date), `{{now}}` (local instant), `{{weekday}}` (local), `{{file_slug}}`. **Use `{{goal_topic}}` for anything fed to a search engine** (strips the routing prefix). Substitution is **value-level** (`substitute_template_vars` walks parsed JSON, replaces inside string values only — quote/backslash/newline-safe).
- **`{{_prev}}` vs `{{_prev.<path>}}`:** `{{_prev}}` = the previous step's output *after* `extract_result_text` unwraps `answer`/single-column `rows` (lossy by design). `{{_prev.<path>}}` (e.g. `{{_prev.id}}`, alias `{{result.id}}`) resolves a dotted path against the **pre-unwrap** envelope (`prev_result_raw`), never distilled. Unresolvable path → **empty string**, never the literal placeholder (consumers read empty as absent). Both forms may co-occur; paths substituted first; strings inserted raw.
- **Per-step model routing:** a step may declare `required_capabilities: [...]`; `services/model_router.rs` picks the best catalog model **the routing policy admits for the step's purpose and `data_class`** (`services/routing.rs` `route()`; the log names every better-ranked model it skipped, with the reason), routed via the `SELECTED_LLM` task-local (precedence: capability-selected > `USE_LOCAL_LLM` background pin > active config). Metadata: `__required_capabilities`, `__data_class`. **A step is private unless it or its chain/schedule file says `data_class: public`** (the seeders stamp a file-level value onto steps), and private work only reaches `no_log` providers. `ROUTE_CONTEXT` is scoped around the job, so `SharedLlm` judges every fallback rung by the same policy. Guards: `private_reasoning_stays_on_a_no_log_model`, `public_reasoning_still_routes_to_gemini_flash`, `private_work_never_reaches_a_training_provider_for_any_capability`. **"Best" = `cost ASC, selection_rank ASC, context_window DESC`** — and since every local/cloud model costs 0.0, **`selection_rank` is the decision** (per model in `models.yaml`, lower wins). Bands: `0–9` free-tier Gemini treated as $0 (only `gemini-2.5-flash`, rank 5 — below ollama-cloud so it wins reasoning at tier 2), `10–99` ollama-cloud, `110–199` local, `210+` paid. Rank is **global, not per-capability**; a single-holder capability is only safe while it stays single. Guards: `selection_order_tests` + `model_config.rs` assert the checked-in `models.yaml` (incl. `reasoning_at_tier2_routes_to_gemini_flash` and `vision_at_tier2_stays_on_the_ollama_cloud_vision_model`). `minimax-m3:cloud` removed 2026-08-31 (left free tier); the seven ollama-cloud entries are the whole free tier. **Gemini free-tier caveat:** `gemini-2.5-flash`/`gemini-3-flash` are catalogued at cost 0.0, which is accurate only on the free tier (429 at the ceiling, no billing) — move them off 0.0 if the deployment ever exceeds it.
- **`CURRENT_TOOL`** task-local attributes every in-job LLM call to `job.tool_name` in the usage ledger. The **chat path does not use it** — `clients/chat.rs` records directly (defaulting to `"chat"`). A **sub-agent** run (`delegate`/`run_agent`) is instead labelled by the `USAGE_TOOL_LABEL` task-local, scoped to `subagent:<agent>` in `AgentRunner::run` around the bounded loop (propagates through `join!`, never a `spawn`); before this its LLM cost billed under `chat`, so `run_agent`/`delegate` had **zero** rows in `model_usage` and sub-agent spend was invisible. Query it with `tool_name LIKE 'subagent:%'`. (2026-09-08)
- **Distilled handoffs (`distill_prev: true`, `distill_max_chars`, `distill_focus`):** `maybe_distill_prev` compresses upstream output on the **local** model before substitution. Soft budget (overshoots ~50%); only hard guarantee is "never longer than raw". Own `LlmClient` at `num_ctx=16384`. **Never** on a step that persists `{{_prev}}` verbatim, nor on evaluator/adversarial steps. Every failure path falls back to raw. Wired in `learn.yaml`, `git-history.yaml`, `video-learning.yaml`.
- **UI chain** (`chains/ui-frontend.yaml`): frontend keywords → `workspace/ui/{{file_slug}}.md`, `no_evaluator: true`.

Full story (routing-capture incident, selection_rank reasoning, distill measurements): history § Externalized Agent Chains.

### Self-knowledge: making running state visible

A model that can't see running work reports it as absent, confidently. Rules that fix the class:

- `manage_scheduled_task(action=list)` is a **tool** (lean payload; `verbose: true` for the rest); **empty-filter guardrail** returns every name + a warning rather than an empty list. `list_tasks` returns **totals** and leads with open work.
- **Truncated tool results are marked** (`truncate_tool_result` → `[TRUNCATED … INCOMPLETE]`). A `reason` result's declared limits are **hoisted to the front** (`annotate_tool_limits`/`reason_limits_marker`). `search_web` results are **prefixed with a numbered source list** (`search_sources_marker`, accepts `link` or `url`). `prepare_tool_result` is the single annotate-then-truncate entry point; the marker leads so truncation can't drop it.
- Failed protocol steps log at **WARN** (`tool_call FAILED`). A **dropped chat turn is reported** (`forward_chat_events`) instead of vanishing — and separately, an **abandoned** one is too: if the SSE client goes away mid-turn the handler future is dropped, that tail never runs, and the turn leaves no trace at all (on 2026-09-11 a turn ran `search_notes`, spent two gpt-oss calls / ~31K prompt tokens, and vanished leaving only an orphaned user row in working memory — indistinguishable in the logs from a request that never arrived). `TurnAbandonGuard` is a `Drop` guard, because cancellation is the one turn-ending path no `await`-side code can report; it is armed for the whole turn and disarmed once the event stream drains, so it never double-reports the dropped-turn case. An **empty completion is retried** (`MAX_EMPTY_COMPLETION_RETRIES`), not mistaken for a finished turn; `FINAL_ROUND_NUDGE` gives a tools-off wrap-up round when tool calls are exhausted. `chat_fallback_ladder` in `models.yaml`; a `reason` fallback to raw prose sets `structured_output_failed` (`confidence 0.0`, WARN).
- **General lesson:** a signal the model must act on belongs at **position zero in a loud delimiter**, not a field — prompt rules do not reliably beat payload position. Behavioural half: `PROJECT-STATUS RULE` in `contexts/general.yaml`.
- **A "what did we learn today / what happened" question is temporal, not topical, and needs a deterministic tool — not a prompt rule and not semantic search.** `recall_recent` (KnowledgeSkill; `KnowledgeStore::recall_window`) counts notes created in a **local-day** window by `note_type` + `source_context` with a bounded recent sample (excludes chunk fragments). It exists because the `general` `PROJECT-STATUS RULE` telling the model to "COUNT FIRST with a neo4j_query" was **ignored** — and, worse, when the orchestrator **delegated** the question to `knowledge-worker`, that profile had neither the rule nor `neo4j_query`, so it semantic-searched the literal date string `2026-09-07` (embeds to nothing), hit its round cap, and reported "no substantive findings" on a 377-note day. The fix is the tool in both `general` and `knowledge-worker` allowlists; a delegated whole-graph aggregate must go to a profile equipped for it. (2026-09-08)

- **★ A tool that reports a COUNT must be able to show the ROWS behind it, and its empty answer must carry the way out of it.** `recall_recent` takes `source_context` / `note_type` filters that narrow **every** aggregation and the sample alike (one shared predicate — `KnowledgeService::window_predicate`), so any bucket it reports is enumerable by asking again with that bucket's name; a filtered call also returns longer snippets (600 vs 200 chars), a larger default `sample_limit` (50), and **`complete`** — whether the sample IS the whole matching set. Why: on 2026-09-11 `recall_recent` correctly returned `video_learning: 43` at position 1, but nothing could enumerate a `source_context` (`search_notes` *requires* a `query` and applies `source_context` as a post-filter on similarity ranking; `list_notes` is an unfiltered last-20). So the `knowledge-worker` sub-agent fell back to `search_notes(query="video learning")`, whose top hit is a month-old IBM video *about* online learning, and told the user **twice** that no videos had been watched — on a day with 11, each with a stored summary — escalating to *"a thorough search… confirmed that no such notes exist"* while **citing its own correct count of 43 in the same breath**. Zero errors, 12 LLM calls: a pure quality miss. **The inversion is the lesson: a count already retrieved outranks a later search that finds nothing.** Second-order trap, hit while verifying the fix: the agent then guessed `note_type:"episodic"` alongside `source_context:"video_learning"` (those notes are `source_record`/`claim`), got `total: 0`, and reported absence again — so a zero-match **filtered** call now re-runs the aggregations **unfiltered** and returns `window_total_notes` + `available_note_types` + `available_source_contexts` with a note saying the FILTER is the likely fault, not the window (same shape as `list_endpoints` pointing a zero result at `list_apis`). A deterministic tool's empty answer must name the values that do exist, because the caller cannot guess a label it has never been shown. Behavioural half: `COUNT-THEN-DRILL` in `contexts/general.yaml` + `contexts/knowledge-worker.yaml`. ### Epistemics: claims, source records, retrieval labelling

Three note types the brain used to conflate: `semantic` (knowledge the brain established), `source_record` (what an external source *said* — video summaries, `news`), `claim` (one checkable proposition + evidentiary status).

- **`(:Note {note_type:'claim', claim_status, asserted_by, asserted_at})`** with `ASSERTED_IN`/`CORROBORATED_BY`/`CONTRADICTED_BY` edges. Status is **derived** from edges (`recompute_status`), never asserted; verification attaches evidence and recomputes, never edits the claim. Support+contradiction → `disputed`; absence → `unverified` (never refuted).
- **`label_claims` (`services/knowledge.rs`) runs in BOTH retrieval paths** — miss one and the unlabelled copy still reaches context. Prefixes claims `[CLAIM · status · asserted by X · date]` and source records `[SOURCE RECORD — …]`, with a humanised age. `claim`/`source_record` are **excluded from consolidation source selection** (consolidation would launder the status away).
- **Claim kind** (`event`/`attribution`/`mechanism`) separates "was asserted" from "is true"; corroborated `attribution` renders "corroborates that it was asserted, not that it is true". **`classify_domains`** tiers corroborating domains (primary/established/unclassified) mechanically and rides it in the label; verification is **never gated** on tier. **`check_independence`** requires `MIN_INDEPENDENT_DOMAINS` (2) distinct non-self-referential domains; recorded on the edge (does not solve true independence).
- **Verification needs a cursor** — "no evidence" is a stable state, so `last_verify_attempt_at` is stamped **before** each attempt and selection orders on `COALESCE(last_verify_attempt_at, epoch) ASC`. Every `verify_one` return path names the `claim`, not just its id.
- **`unsourced_synthesis`** (retrieval-labelled, excluded from consolidation) is the type for the brain's own uncited reasoning; migrating a writer does not fix prior writes (`scripts/migrate_unsourced_gap_notes.cypher`). **A data fix and a code fix are separate deliverables.**
- Chain-extracted claims get their `ASSERTED_IN` edge via `{{_prev.id}}` + `prev_result_raw`. The `claim` tool **echoes its input as `answer`** (safe to insert mid-chain). Standing schedules write `source_record` (not `semantic`) + a claim-extraction step + a `source_list` + a recency gate.

**Everything stored stays UTC; everything said is local.** Local time needs both `TZ`/`BRAIN_TIMEZONE` in the env *and* code asking for local (both failures silent) — `log_resolved_timezone()` warns at startup when unconfigured. Resolution: `BRAIN_TIMEZONE` → `TZ` → `/etc/localtime` → UTC. `TZ` on `agent-brain` only, not `neo4j`. The four date-producing call sites (chat prompt, both scheduler substitution sites, constructor) are local; `services/sleep.rs` keeps UTC for filenames. `now_stamp()` renders a fully-qualified instant per turn; `{{now}}`/`{{weekday}}` template vars; `label_claims` appends humanised age. Behavioural half: `TIME RULE` in `contexts/general.yaml`. Full story: history § sense of time.

### Tool-integrated reasoning (`execute_code` + `sandbox` sidecar)

Lets a step *compute* its figures instead of hallucinating them; a wrong number becomes a traceback. **Execution never happens in the brain process** — `skills/exec.rs` is an HTTP client for the `sandbox` compose service. Isolation contract (in `docker-compose.yml`): **`sandbox-net` is `internal: true`** (no egress — the only real boundary), no `env_file` (no creds), no bind mounts, `read_only` root, `cap_drop: ALL`, `no-new-privileges`, `mem_limit: 2g`, `pids_limit: 128`, tmpfs `/tmp` `noexec`. **Do not put `sandbox` on `brain-internal` and do not add a `ports:` mapping.** Per-run limits in `sandbox/server.py`. **A failed run is a successful tool call** (`isError: false`, traceback in `stderr`) — a tool *error* would burn a retry and fail the owning Task. No state between calls; pass all input inline. `numpy`/`sympy`/`pandas` installed at build time (no run-time network). Routing: `computation` capability held by **`qwen2.5-coder:7b` alone** (`selection_rank 150`); `execute_code` in `general`/`self-analyst` allowlists. Behavioural half: `COMPUTATION RULE`.

**Rust goes through the same tool: `execute_code(language: "rust")` → the `rust-sandbox` service** (`RUST_SANDBOX_URL`). Takes `code` (a `main.rs`, `cargo run`) or `files` (a crate as path→content, default `cargo test`), plus `command` (`test`/`check`/`clippy`/`run`/`build`) and `include_ignored`; the result adds `tests_passed`/`tests_failed`/`compile_failed`. A language is only offered in the schema when its sandbox URL is set, and `language` defaults to `python` so existing callers are unchanged. **Same isolation contract, two deliberate differences:** its `/work` tmpfs is **exec** (Rust must run the test binaries it compiles), and crates come from a **read-only cache fetched at image build** from `rust-sandbox/crates/Cargo.toml` with cargo run `--offline` — an uncached crate fails to resolve and the server appends the available list. The linker needs `TMPDIR`/`HOME` inside the writable scratch or it fails `Cannot create temporary file in ./: Read-only file system`. It runs as UID **10001**, not 1000, because `RLIMIT_NPROC` counts per real UID kernel-wide (the Python `sandbox` still shares UID 1000 with the host user). Built for `project-docs/RUST_FINETUNE_EXPERIMENT.md`. Full story: history § Tool-integrated reasoning.

### Going local: what moved off `gpt-oss:120b-cloud` (2026-09-11)

Measured over 7 days, then migrated. Every spawnable sub-agent except one is pinned `model_preference: gemma4-e4b` / `provider_hint: llamacpp`, as is the front door.

- **The budget is the constraint, and it is roomier than assumed.** Sidecar is `-c 32768 -np 2` ⇒ **16384/request**. Observed 7-day maxima: `api-scout` 7036, `api-integrator` 5935, `knowledge-worker` 5458, `researcher` 5320, `code-analyst` 4249, `job-applicant` 2450, `schedule-author` 2188. All ≤ 43%. An earlier claim that `researcher`/`code-analyst` would overflow was wrong — check the ledger before asserting a ceiling.
- **`reason` is the one that does NOT fit**: avg 20395, max 43493, and 6 of 17 calls errored *on gpt-oss*. Leave it on cloud, or raise `-c` (VRAM allows ~+1.3 GB; `-np 1` would fix context but serialises the front door against its own workers).
- **★ The limit on going local is RESULT-DIRECTED ITERATION, not context and not hop count.** Head-to-head 2026-09-11: each locally-pinned agent against a byte-identical cloud twin (same tools, same prompt, only the model differs), invoked through `run_agent` directly so the front door could not contaminate the comparison. Every failure was `isError: false` — the error counter cannot see any of this.

  | agent | local calls | cloud calls | local outcome |
  |---|---|---|---|
  | `schedule-author` | 0 | 0 | **PASS** — lint-clean draft (`provider_hint` top-level, `context: "{{_prev}}"`, `source_context` present) |
  | `code-analyst` | 8 | 8 | FAIL — never used the `path:line` its own grep returned |
  | `researcher` | 4 | 8 | FAIL — no `http_request`, no manufacturers, declined to cite a figure it held |
  | `api-scout` | 3 | 8 | FAIL — verified nothing, returned no base URL or endpoint |
  | `api-integrator` | 1 | 8 | FAIL — quit when the first probe failed |
  | `toolsmith` | **0** | 1 | FAIL — guessed the tool inventory from memory instead of calling `analyze_own_structure`, and leaked chain-of-thought as `step_by_step_thought` |

  E4B fails in two opposite-looking ways — stopping after one call, and looping eight without progress — and both are the same defect: **the result of step N does not shape step N+1.** It halts at the first obstacle or repeats undirected. The cloud model closes the loop (failed probe → search for docs → retry; search hits → probe the candidate → confirm).

  **So the predictor is the shape of the task, not its size.** Local is safe where there is no loop to close: one-shot synthesis (`schedule-author` drafts in a single pass) or a deterministic tool that *returns the answer* (`knowledge-worker`'s `recall_recent`). Everything investigative — where each step is a judgement about what the last result implies — needs cloud. A profile's token budget says nothing about this; `code-analyst` was migrated on a 26%-of-budget measurement and failed anyway. **Measure the ANSWER against a twin before pinning an agent local.**
- **`job-applicant` stays on cloud deliberately** — it fits easily, but it drafts real résumé content for real submissions; quality risk with consequences off this machine.
- **Do not swap the sidecar to Qwen3.** That comparison already ran: Qwen3-8B 6.0 GB / 70 tok/s vs E4B 3.3 GB and ~14% faster, and with bge-m3 + whisper resident there is ~3.0 GB free — Qwen3-8B will not fit alongside a 32k KV pool. Put more work *on* E4B instead.
- **`-np 2` means two local slots.** Front door + one sub-agent saturates it; background jobs already use llamacpp. Contention shows up as latency, absorbed by `OLLAMA_LOCAL_TIMEOUT_SECS`.

**★ A local model's failure is usually a TOOL contract, not model capacity.** A delegated `code-analyst` on E4B reported the queue's retry logic "not present in the knowledge base" — on a codebase where `max_attempts` has 50 hits. The model was right to say so: `search_codebase` is a **literal regex grep**, it was handed a prose question, and it returned an empty result naming nothing to try next. gpt-oss would have hit the identical wall. Two model-agnostic fixes, both the `recall_recent` count-then-drill doctrine applied again: (1) `search_codebase`'s zero-result path now re-probes each significant term (stopword-filtered, counts marked `N+` at the probe cap since an exact count would be a lie at the ceiling) and states plainly that it is literal, not semantic — "absence of the phrase is NOT absence of the code"; (2) `contexts/code-analyst.yaml` gained a LOCATE→READ→reason workflow, because the agent had `read_codebase_file` and never called it, and `reason` retrieves NOTES — which is how a doc's "lacks exponential backoff" claim got reported as a finding about the source. It also passes `file_pattern: ".rs"` now, after an unfiltered grep sent it to summarise CLAUDE.md instead of `queue.rs`. **When a local model underperforms, check what its tools actually returned before concluding the model is too small.** **Same class, also fixed:** `read_codebase_file` had `max_lines` (default 500, cap 2000) and a truncation marker but **no offset**, so everything past line 2000 of a 2790-line file was unreachable at any setting and an agent asked about logic at line ~1572 correctly reported it "not visible in the files examined". It now takes **`start_line`** (1-indexed, matching the `path:line` citations `search_codebase` emits), states the window it returned (`lines 2780-2784 of 2790`), and its continuation marker names the exact next call rather than the dead-end "use max_lines to read more". Past-the-end reads report the valid range instead of an empty result.

### Web Search: engine failover ladder + usage ledger

`search_web` walks an ordered **ladder** (`SEARCH_ENGINE_ORDER`, default `searxng,google,serpapi,brave`) until one answers **with results**.

- **`searxng` leads** (self-hosted, no key/quota; `brain-internal` only, disabled `limiter` — do not add a `ports:` mapping without re-enabling it; keep `json` in `search.formats`). A **requested `engine:` is promoted, not made exclusive.** **Quota cooldown** (`QUOTA_COOLDOWN_HOURS` 6) moves an exhausted engine to the back, not out. Results normalised to `link`/`snippet`. Every attempt writes a `search_usage` row; `get_search_usage` reports per-engine + per-day.
- **An engine with no credentials is dropped from the ladder outright, not demoted** (`is_engine_configured` + `retain_configured` in `engine_ladder`). Unlike a spent quota (which recovers overnight, so demote), a missing key never fixes itself at runtime, and it fails `not_configured` on *every* call — the 2026-09-08 GDELT session put `engine: google` on each search with no `GOOGLE_API_KEY`, wasting the first rung and a WARN line on every one and helping exhaust the 8-round chat budget twice. `searxng` needs no key (always kept); `google` needs key **and** CX; `serpapi`/`google_news` share one key; `brave` needs a key. Never empties the ladder: if nothing is configured the original is kept so the caller still gets a real per-engine error. An unknown engine name is assumed configured. Guards: `unconfigured_engines_are_dropped_from_the_ladder` + siblings in `search.rs` tests.
- **Zero results is not an answer** — a rung returning `200` + empty falls through to the next; if *all* rungs come back empty, return `[]` (erroring would burn retries). Fall-through logged at WARN.
- **SerpApi signals failure as HTTP 200 + `{"error":…}`, not a 4xx/5xx** (quota, rate, "couldn't get valid results"). `search_serpapi`/`search_serpapi_news` check the `error` field and return it as a real failure (raw message → `classify_search_error` → the ladder WARNs, records the right `error_kind`, and demotes on quota). Before this fix (2026-09-08) that response was read as `success` with 0 results and the ladder fell through to SearXNG **silently** — a real SerpApi outage looked like success in the logs and over-counted `serpapi` in the ledger. A genuinely-empty result with no `error` field is still a real empty (falls through with the zero-results WARN, no cooldown). **`unresponsive_engines` in the JSON is the diagnostic** (distinguishes "cannot connect" from "connected and refused"); `scripts/searxng_engine_health.py` probes both evergreen and fresh query shapes. **Never probe a single engine with `&engines=<name>`** (silent fallback to the default set); attribute by each result's own `engine` field. A relevance failure cannot be caught by a count.
- **News: `engine: "google_news"`** (`search_serpapi_news`, SerpApi `engine=google_news`). SerpApi free tier is **250/month** (not 100); `serpapi`+`google_news` share one account (ladder demotes both when either is exhausted). No `source_list` on Google News steps. `google_news` is **not** in the default ladder. **Query rewriting was investigated and rejected** (null result — the queries were never the problem; the blocked engines were). **Quota exhaustion alerts** (`is_quota_exhausted_error`, deduped `:AgentNotification` once/tool/24h).

Full story (the four outages — DNS/empty results, bot-blocks, junk results — and the query-rewriting A/B): history § Web Search.

### Media Learning (watch & summarize videos)

**★ A LIVE broadcast is rejected up front, and `MEDIA_MAX_DURATION_SECS` cannot do it for you.** `fetch_via_ytdlp` bails on `meta.is_live` **before** the caption path. Two independent reasons the old cost guard never fired: it lives on the *no-captions* branch only (a live stream with auto-captions skips it entirely), and yt-dlp reports `duration: null` for a live stream, which parses to `0` — so `0 > 10800` is false. A live broadcast also has no end, so `ingest_media`'s map-reduce has no finite transcript and the job simply hangs. `was_live` (a finished stream, now a normal VOD with a real duration) is deliberately NOT treated as live. Observed 2026-09-11: a `watch video:` task on a broadcasting stream held one of the two local job slots for **3 hours across 29 attempts**, burning zero LLM calls and recording no error.

**`poll_media_sources` filters `is_live` at DISCOVERY too, so a live stream never becomes a Task** — no chain, no retry cycle, no failed owning Task. The probe is deliberately no longer gated on `MEDIA_MAX_DURATION_SECS > 0`, because a live broadcast is unbounded whatever cap is configured. **It records NO dedup `:Media` node**, unlike the over-length path: a video's duration never changes, so `skipped_too_long` is correctly permanent, but "live" is TEMPORARY — the broadcast ends and YouTube republishes it as an ordinary video. A `skipped_live` node would make `media_exists()` suppress the finished recording forever. It stays in the channel RSS feed, so the next poll re-probes and picks it up once `is_live` is false. Motivating source: `c-span`, the highest-volume watchlist entry (25 tasks in 7 days) and the one that broadcasts live.

**`chains/video-learning.yaml` passes `{{goal_topic}}`, never `{{goal}}`.** The task goal is `watch video: <url>`, so `{{goal}}` hands `ingest_media` a URL with the routing prefix glued on. This is the same rule CLAUDE.md already states for search steps — it applies to **anything consumed as data**, not just search engines.



`MediaSkill` (`skills/media.rs`) + `MediaService` (`services/media.rs`); spec in `project-docs/VIDEO_LEARNING_PLAN.md`. Captions-first (`yt-dlp` downloads the caption file, parse `json3`); Whisper fallback (`WHISPER_PROVIDER` set → POST audio to OpenAI-compatible endpoint via `services/transcribe.rs`); `WHISPER_PROVIDER=none` errors caption-less videos cleanly. **Map-reduce summarization happens inside `ingest_media`** (transcripts aren't fixed-length, chains are). On-demand: `ingest_media(url)`, `fetch_transcript(url)`; a `watch video:` Task routes to `chains/video-learning.yaml`. Autonomous: `poll_media_sources` (RSS → `watch video:` Task fan-out, `MEDIA_WATCH_ENABLED`-gated, duration pre-filter via `fetch_meta`), `discover_media_sources` (weekly, stages **inactive** sources for review). Phase 5 (podcast RSS + local files) implemented. **`list_feed_videos` retries transient feed failures with backoff** (3 attempts, 500ms→2s): YouTube throttles the endpoint with 404/429/5xx when a poll fans every source at once, and the *same* channel_id returns 200 minutes later — a bare `error_for_status()?` dropped each source for a whole 12h cycle. ### Context Profiles

YAML in `contexts/` define tool allowlists + system prompts per persona; `boot.yaml` runs every startup, `init.yaml` on empty graph; `auto_assign(goal)` keyword-matches. **A profile applies four layers to a chat turn**: `tools` allowlist filters the registry, `system_prompt` appended after the base, `pre_load_query` output appended under `LIVE SELF-STATE` (all three via `build_system_prompt`), and **`model_preference` (+ optional `provider_hint`) overrides the chat model for that turn** (`ChatService::resolve_profile_model` in `clients/chat.rs`). The model is resolved against the DuckDB catalog (exact key/model match → substring for legacy aliases like `sonnet`/`haiku` → `provider_hint` for a non-catalog model), and credentials/endpoint come from the env via `config_for_catalog_entry`, so the checked-in YAML never carries a key; the chat fallback ladder still applies on top (an unreachable pin — e.g. an Anthropic model with no key — falls down it). An unresolvable/blank preference keeps the chat default. **This is honored ONLY on the human `/chat` path, not background jobs** (those use capability routing / `provider_hint`). **Every model a profile turn may use is judged by the routing policy** (`services/routing.rs`), by the profile's **`data_class`** (absent ⇒ `private`, which admits only `no_log` providers). On `/chat` a refused pin is announced in the stream (`⚙ profile model … refused`) and the turn keeps the chat default; every ladder rung and the synthesis model are judged too, and with no admitted rung the turn fails loudly. **A sub-agent (`AgentRunner::run`, i.e. `run_agent`/`delegate`) runs as `purpose: subagent` with the stricter of its caller's and its profile's class**, which refuses paid providers unless `ROUTING_PAID_FOR` names `subagent`, and refuses providers whose declared limits cannot carry a multi-round loop (rpm < 20 or rpd < 500: the Gemini 5-RPM trap, OpenRouter's 50/day). This replaced the provider-type clamp (2026-09-15). **The front door `GeneralDefault-Orchrestator` is `data_class: public` by decision (2026-09-15) and keeps `gemini-2.5-flash`**: everything typed through it may be used by Google. `researcher` is private; `api-scout` public. `save_profile` keeps a stored `data_class` when a save omits it, so a UI edit cannot silently flip a profile private. **Routing a sub-agent to the local llama.cpp e4b sidecar** (2026-09-10) needed three changes, not just the clamp: `config_for_catalog_entry` gained a `llamacpp` branch (→ `LlmProviderType::LlamaCpp` @ `LLAMACPP_URL`, embeddings pinned to host Ollama — before this every non-cloud provider collapsed to host Ollama at `OLLAMA_LOCAL_URL`, so a pin could never reach the sidecar); the loop dispatch (`run_one_attempt`) routes `LlamaCpp` to `run_ollama_cloud_loop` (the OpenAI-compat, tool-call-accumulating loop — NOT the degraded `run_text_loop`); and a `gemma4-e4b` catalog entry (`models.yaml`, provider `llamacpp`) exists so a profile can resolve the pin. **VERIFIED 2026-09-11 — Gemma-4-E4B drives multi-round tool loops in production.** `knowledge-worker` is pinned to it (`model_preference: gemma4-e4b`, `provider_hint: llamacpp`) and runs 7-9 round loops with zero errors (`tokens_in` climbing 3.8k→8.0k, `tokens_out` dipping to 23-24, which is a compact tool-call emission). `contexts/knowledge-local.yaml` was never created; `scripts/probe_e4b_subagent.py` targets it and so has never run — the production ledger is the evidence instead. Peak observed `tokens_in` is 7959, **49% of the sidecar's 16384/request budget** (`-c 32768 -np 2`), which is the real ceiling on moving context-hungry workers (`researcher`, `code-analyst`) local. A **bare `provider_hint` with no `model_preference` is inert** (the resolver is only reached via `model_preference`), so a sub-agent profile that wants local must set `model_preference`, not just the hint. The `:ContextProfile` `model_preference`/`provider_hint` are also mirrored to the meta-graph and echoed by `/api/models` + the frontend "🤖 Agents" modal, which writes them via `/api/contexts`. **`pre_load_query` accepts Cypher or a keyword** — read-only Cypher runs verbatim (`is_read_cypher()` rejects any write token); a failing query warns and continues. `contexts/self-analyst.yaml` is the self-inspection persona (injects `:ModelDef`/`:SchedulerChain`/`:ScheduledTask`/`:ToolDef` live state; enforces MEASURE→LOCATE→COMPARE→PROPOSE). `contexts/general.yaml` carries a smaller version + read-only introspection tools.

**★ The front door (`CHAT_DEFAULT_PROFILE`, 2026-09-11).** The chat default is env-selected via `default_profile_name()` (`services/context_builder.rs`), not a code constant; `contexts/general-default-orchestrator.yaml` (`GeneralDefault-Orchrestator`, pinned to local `gemma4-e4b`) is what compose points it at. Four load-bearing rules:
- **When `CHAT_DEFAULT_PROFILE` is set, the chat path SKIPS `auto_assign`.** Keyword routing and roster delegation are two routers, and `auto_assign` runs first, so the dumber one always wins: on 2026-09-11 "What did we learn today?" scored `knowledge-worker`, ran it as the *persona*, answered off its own `recall_recent`, and never reached the orchestrator. The front door IS the router — it reads the live roster and picks with `delegate`. An explicit request `context_profile` and the `jobsearch-` session pin both still win; set the var empty to restore `auto_assign`.
- **The front door is a router, so it has routing misses of its own — and they cost a whole turn while recording `success: true` on every row.** Measured 2026-09-11/12: "what did we learn recently" and "how many agents do we have" both went to `researcher` (a WEB profile holding no `recall_recent`, no `neo4j_query`, no `describe_graph`), which burned all 8 rounds and reported absence — the 2026-09-08 delegated-recall false negative recurring one layer up, now caused by the orchestrator's choice rather than `auto_assign`. Anything about the brain's own tools, agents, schedules, tasks, or stored notes goes to `knowledge-worker`; `ABOUT THE BRAIN ITSELF` in the front-door prompt says so in four lines. Also note `run_agent(agent:"auto")` is a **token-overlap** matcher: "how many **agents**" matches `researcher` on the word alone, so a meta-question must never be left to auto-select.
- **The default profile is excluded from `auto_assign` candidates** (it is the fallback; matching it explicitly would shadow a real specialist), and `delete_profile` protects it as well as `general`.
- **`delegate` is chat-loop only and is NEVER in the MCP tool registry.** A profile used for `MCP_TOOL_PROFILE` must therefore include **`run_agent`** (the registered equivalent) or an MCP client gets the allowlist with no dispatch path at all — strictly worse than the full registry. Both vars point at the front door, so a connecting client sees 7 tools instead of ~42.
- **★ A front-door prompt is a SIZE BUDGET on a small local model.** Same model, same tools, same question: at 2332 chars E4B delegates; at 6801 it emits prose and refuses. The added bytes were `general.yaml`'s ABSENCE / TOOL-RESULT / CITATION rules — all of which say *don't overclaim* — and a 4B model over-applies them into the exact "I cannot determine this" they exist to prevent. Those rules are persuasive narratives written for a large model. Keep a local profile's prompt near 2-3k chars (the front door is at 4.0k after the `ABOUT THE BRAIN ITSELF` rule and still delegates — re-measure if it grows again), write rules as terse imperatives, and include an explicit floor ("When in doubt, DELEGATE; never answer 'I cannot determine this' without having called delegate at least once this turn"). Narrative rationale belongs in history, never in a local model's prompt.

Full detail: history § Context Profiles.

## Critical Dev Notes

> Long root-cause narratives for the starred rules live verbatim in **`project-docs/engineering-history.md`** (§ *Critical Dev Notes*).

**LlmConfig:** `base_url` is `Option<String>`. Default model `"qwen3.5:4b"`. Tests: `config.base_url.as_deref()`.

**Structured LLM output:** for strict JSON, call `LlmProvider::generate_json(prompt, system, required_keys, max_retries)` (self-correcting re-prompt loop) rather than hand-rolling `generate` + `extract_json` + `from_str().unwrap_or_else`. `extract_json` picks the **earliest-opening** delimiter; pass `&[]` for `required_keys` to accept any valid JSON.

**★ Pick the local model by VRAM residency, not leaderboard.** Residency is a cliff, not a curve: every model that fits generates at 67–125 tok/s, one that doesn't (`gemma4:latest`, 9.86 GB on an 8 GB card) at ~26. Models don't co-reside here — a swap is a replacement; unload the outgoing model (`keep_alive: 0`). **`granite4:latest`** is the local model (`OLLAMA_LOCAL_MODEL` in compose; already `selection_rank 120`), 18× faster than `gemma4` in production. Benchmark the **structured** path too (a fast model can emit unparseable JSON), and beware thinking models — `qwen3.5:4b` (the stale `DEFAULT_MODEL` in `llm.rs`) emits into `thinking` and returns an **empty** `response`. Output length is a cost, not a quality signal. Full tables: history.

**★ The local model has its own timeout.** `OLLAMA_LOCAL_TIMEOUT_SECS` (default **600**) applies to the local background config alone (built in `brain_core.rs`); cloud calls keep the 120s default. It's burstiness, not average load — `poll_media_sources` fans ~30 videos out at once; at 30–75 calls/hour latency climbs to 120s and every call clips. Killing a call at 120s throws away spent compute *and* the chain built on it. Not the cause: concurrency (Ollama batches) or Ollama being down. Full incident (the `0426218` fan-out move): history.

**★ llama.cpp backend for background jobs.** The generation backend for `provider_hint:"ollama"` steps is env-selectable via `LOCAL_LLM_BACKEND` (`ollama` | `llamacpp`); the switch is in `services/llm.rs::build_local_llm_config`, used by both `brain_core.rs` and `scheduler.rs`. `LlmProviderType::LlamaCpp` reuses the existing OpenAI-compatible provider (`openai_compat.rs`) — llama.cpp's `llama-server` speaks the same `/v1/chat/completions` wire format as Ollama Cloud. **Load-bearing facts:** (1) **Embeddings never move** — `build_local_llm_config` pins `embed_base_url` to `OLLAMA_LOCAL_URL` no matter the backend, because a single-model `llama-server` doesn't serve `/api/embeddings`; host Ollama stays up for bge-m3. (2) `keep_alive`/`num_ctx` are Ollama-native and **ignored** by the llama.cpp provider — set context/offload as `llama-server` launch flags in the compose `command:` (`-c`, `-ngl`, `--flash-attn`, `--cache-type-k/v`), not per-request. (3) `USE_LOCAL_LLM` routing is backend-agnostic (keyed on the flag, not the provider type), so a llama.cpp local route is still `is_local_route=true` and never falls back to cloud. (4) **The local model is a thinking model** — background steps that parse JSON need thinking OFF or the reasoning leaks into `content` and no JSON is emitted. **The flag is model-specific**: Qwen3 honors `--reasoning-budget 0`; **Gemma 4 IGNORES it and needs `--reasoning off`** (verified 2026-09-10 — E4B leaked its whole thought process until switched). Current production model is **Gemma-4-E4B** (`--reasoning off`), chosen over Qwen3-8B because it's fully resident at ~3.3 GB (weights) vs 6.0 GB and ~14% faster — see the residency note below. Provider variant + `build_local_llm_config` are covered by the lib tests; scope of the switch is background jobs only — human `/chat` stays on Ollama-Cloud.

**★ The llama.cpp CUDA image must match the host driver (`llamacpp/Dockerfile`).** The GPU is an RTX 3060 Ti (8 GB, sm_86); the host driver is **535 / CUDA 12.2**. The upstream prebuilt `ghcr.io/ggml-org/llama.cpp:server-cuda` ships **CUDA 12.8** and will NOT run on this driver: its bundled forward-compat stub (`libcuda.so.570`) aborts CUDA init on a GeForce (`forward compatibility was attempted on non supported HW` → silent CPU fallback), and even with the stub removed the 12.8 cubins fail to load (`CUDA error: device kernel image is invalid`). So the sidecar is **built from source against CUDA 12.2** targeting sm_86. Two build gotchas the Dockerfile encodes: link with `-Wl,--allow-shlib-undefined` (libggml-cuda references CUDA Driver-API symbols the devel image keeps in `lib64/stubs`; they resolve at runtime when cudart loads the injected `libcuda.so.1`), and enable `-DLLAMA_OPENSSL=ON` + `libssl-dev`/`libssl3` (b10900's `-hf` downloader uses a native TLS client — without it, `HTTPS is not supported` and it can only load an already-cached GGUF). The production model **Gemma-4-E4B Q4_K_M sits ~3.3 GB** on the GPU (4.6 GB with the 16k KV cache) alongside bge-m3 and the whisper sidecar, leaving ~2.8 GB free. (It replaced Qwen3-8B at 6.0 GB / 70 tok/s: E4B is ~14% faster and half the VRAM — Gemma-3-**12B does not fit resident** on 8 GB, spilling to ~21 tok/s.) Full rationale in the Dockerfile header; benchmark detail in the memory note `llamacpp-switch`.

**A `reqwest` failure says what went wrong.** `describe_reqwest` (`llm_providers/mod.rs`) prefixes the kind (`operation timed out:` / `connection refused:`) — the "why" lives in `source()`, which `Display` drops — and appends the full cause chain. The prefix survives job-`error` truncation and matches the phrases `classify_unavailable` uses.

**Every failed LLM call records an `error_kind`.** `SharedLlm::generate`'s per-call `record_model_usage` used to hardcode `None`; now every attempt (primary and each fallback rung) goes through `run_and_record`, whose `failure_kind` reuses `classify_unavailable` and falls back to `"other"`.

**★ A cloud LLM that cannot answer walks a fallback chain; one that answers and refuses does not.** `classify_unavailable` (`services/shared_llm.rs`) qualifies four kinds: `rate_limited`, `subscription_required` (403 "requires a subscription"), `transport` (DNS/refused/TLS/client timeout — never reached the provider), `server_error` (5xx). Anything else propagates (falling back on a 400/401 just gets a worse rejection). `is_server_error` matches canonical reason phrases, not bare numbers (`contains("500")` fires on token counts). Fallback is guarded by `!is_local_route` (a local model never retries against itself) and the chain order comes from `build_fallback_chain`: a **capability-selected** cloud route (e.g. a `reasoning` step routed to `gemini-2.5-flash`) falls back to the **active config first** — the free Ollama-Cloud model, which does not share the selected model's quota, i.e. "what we were doing before" — and only then to local; a route that WAS the active config skips straight to local. This is why routing reasoning at `gemini-2.5-flash` and hitting its 1500 RPD ceiling degrades to `gpt-oss:120b-cloud`, not to weak local granite4. Each rung (primary included) records its own `model_usage` row via `run_and_record`. Full incident (the lost off-grid report): history.

The **chat path has its own ladder** (`chat_fallback_ladder` in `models.yaml`, walked by `run_one_attempt` in `clients/chat.rs`) — it turns on "did the turn produce output", not the error class, and is unmetered-cloud→local (no metered/rate-limited rung). **`run_bounded_loop` (the sub-agent loop behind `run_agent`/`delegate`) walks that same ladder**, so a transient 500 on a sub-agent's primary model degrades to the next rung instead of surfacing the raw error as the whole delegated answer — consistent with the sub-agent unmetered clamp (the ladder introduces no metered rung). Before this it dispatched a single provider loop with no fallback and failed a delegated task on a provider blip.

**Skill registration:** register to BOTH `tool_registry` (for `tools/list`) AND the `skills` vec (for `tools/call`). Forgetting either = invisible tool or dispatch failure.

**★ Ollama serves a 4096-token context by default, whatever the model claims** — input past the window is **truncated silently**. Put the operative instruction **before and after** a large payload, never only after. `LlmConfig::num_ctx` (`Option<u32>`, default `None`) sets it per config; only the distiller raises it (`DISTILL_NUM_CTX=16384`). Detail: history.

**★ Embedding fails on LENGTH, and the limit is TOKENS — the old "`500 … NaN` for certain strings" diagnosis was wrong.** Probed against the live `bge-m3` 2026-09-12: emoji, control chars, zero-width joiners, CJK, punctuation and whitespace-only input all embed cleanly at 1024 dims. Two real failure modes: **empty input returns HTTP 200 with a ZERO-LENGTH vector** (worse than an error — it flows into `db.index.vector.queryNodes` as a silent no-op reading as "nothing is similar"), and **over-length input 500s**. The ceiling is ~3,200 tokens, which is **~10,327 chars of prose but only ~5,819 of dense JSON/URL content** — so a character cap cannot be right for both, and one set from the prose measurement still 500'd on 3 of the 4 notes it was meant to repair. `prepare_embed_input` (`llm_providers/mod.rs`) rejects empty and caps at **4,000 chars** on a char boundary (compile-time `const _: () = assert!` pins it below the measured dense ceiling); `embed_with_backoff` halves and retries up to 3× on a length-shaped failure only — a missing key is not retried. Wired into all three providers. Nothing truncated before this, so 4 notes (longest **201,259 chars**) sat unembedded and invisible to vector search; backfilled. Both vector-search entry points still degrade to the BM25 `note_content_fulltext` index (`search_notes_inner`, `fetch_similar_notes`) and any new embed call site must too — and `search_notes_inner` now **WARNs** when it does, because the `Err` was silently discarded by a let-chain, which is precisely why a wrong folk diagnosis survived for months. The BM25 fallback must run its query through `sanitize_lucene_query`. (2026-09-12)

**★ `neo4j_query`, and the graph's timestamps.** LIMIT injection now matches `RETURN`/`LIMIT` as whitespace-separated words (a substring test sent `LIMIT 20 LIMIT 100`). **Every temporal property is a native `DATETIME` in UTC** — read `project-docs/schema.md` § "Timestamps: one representation, always" before writing date Cypher (Cypher compares a temporal to a string as **null**, not false, so a mismatch silently drops the row and the query succeeds with zero results). Use `datetime($param)` on writes, compare against `datetime(...)`, `toString(prop)` when reading into a `String`, `repository::node_ts` for whole-node reads. Guards: `string_timestamp_violations()` (startup WARN), `no_string_timestamps` (integration test), and a `neo4j_query` hint on a zero-row date-literal filter. Migration: `scripts/migrate_timestamps_to_datetime.cypher` (run with the brain **stopped**). Full incident (the "we learned nothing" / 504-notes day): history.

**`McpServer`** is a thin backward-compatible wrapper around `McpServerCore` (stdio path only).

**HTTP session init:** always send `notifications/initialized` AFTER `initialize`, or the server stays `Initializing` and rejects all tool calls.

**Initialization order:** `SchedulerService::new()` after `QueueService::new()`; `QueueService::spawn_coordinator()` after the tool handler is set (end of `build_skills`).

**Consolidation loop:** uses `[Memory N]` labels (not `Note N:`). Source selection excludes LLM-generated types and only considers notes whose `next_review_at` is due (without the due filter the fixed topic embedding re-selects the same top-K every cycle). Empty selection is a no-op success. Source notes get `next_review_at = now + 30 days`.

**`services/mod.rs`:** must re-export `pub use llm::{LlmClient, LlmConfig, LlmProviderType};`

**Context Profiles:** YAML in `contexts/` (`CONTEXTS_DIR`). Loaded by `ContextBuilderService::load_profiles()` in `build_skills()`. `boot.yaml` runs after each `build_skills()`, `init.yaml` on an empty graph. `ContextSkill` registered when `context_builder_arc` is `Some`.
